# Internationalization (i18n)

`tisvlay-gui` is wired for translation via gettext, even though only English ships at v1. It owns the `tisvlay-gui` gettext domain and `.pot` template; per-locale catalogs live under `crates/tisvlay-gui/lang/<locale>/LC_MESSAGES/tisvlay-gui.po`. Missing `.mo` falls back to the literal source strings, so the workspace is always shippable.

> **Tray status:** the current tray is not gettext-wired — its re-wiring (restoring the two-domain layout this document describes: own `tisvlay-tray` domain, build.rs-compiled `.mo`, tray pass in `just i18n-extract`) is tracked in [ideas/switchover-followups.md](ideas/switchover-followups.md). The tray-specific instructions below describe that target state.

## Architecture

- **Slint strings** (GUI only) wrap literals with `@tr("…")` in every `.slint` file. The `slint = { features = ["gettext"] }` feature flag activates Slint's built-in gettext lookup; `slint::init_translations!(…)` in [crates/tisvlay-gui/src/lib.rs](../crates/tisvlay-gui/src/lib.rs) binds the `lang/<locale>/LC_MESSAGES/tisvlay-gui.mo` directory.
- **Rust user-facing strings** (GUI errors, schema field labels pushed from vendor backends, tray menu / tooltip / status / startup-error text) wrap literals with `gettextrs::gettext("…")`. In the GUI they share the same gettext catalog as Slint's `@tr` — one `.mo` per locale serves both layers. The tray uses the same gettext-rs API against its own catalog; init lives at the top of [crates/tisvlay-tray/src/main.rs](../crates/tisvlay-tray/src/main.rs) (explicit `bindtextdomain` + `textdomain` against `CARGO_MANIFEST_DIR/lang`).
- **Vendor backend crates** (`tisvlay-lg`, future `tisvlay-samsung`) own their own user-facing strings (input names, profile names, vendor-specific schema labels). v1 wraps the surrounding tray/GUI labels only; per-vendor `.mo` files are deferred follow-up work.

## Catalog layout

```
crates/tisvlay-gui/lang/
├── tisvlay-gui.pot                                      # template, committed
└── <locale>/LC_MESSAGES/tisvlay-gui.{po,mo}             # per-locale, .mo built by slint_build

crates/tisvlay-tray/lang/
├── tisvlay-tray.pot                                     # template, committed
└── <locale>/LC_MESSAGES/tisvlay-tray.{po,mo}            # per-locale, .mo built by crates/tisvlay-tray/build.rs
```

`.pot` templates are committed; `.po` files land as translators contribute them; `.mo` files are build artifacts and never checked in.

## Workflow

```bash
just i18n-extract        # rebuild both crates' .pot templates
just i18n-extract-gui    # GUI only (Rust + Slint passes)
just i18n-extract-tray   # tray only (Rust pass)
just i18n-update         # merge refreshed .pot into existing .po files
```

Run `just i18n-extract` whenever you add or change user-facing strings; review the resulting `.pot` diff and commit. `cargo build` regenerates `.mo` files at compile time — `slint_build` for the GUI, [crates/tisvlay-tray/build.rs](../crates/tisvlay-tray/build.rs) for the tray.

### Adding a new locale

```bash
# GUI
msginit -i crates/tisvlay-gui/lang/tisvlay-gui.pot \
    -l fr_FR \
    -o crates/tisvlay-gui/lang/fr/LC_MESSAGES/tisvlay-gui.po

# Tray
msginit -i crates/tisvlay-tray/lang/tisvlay-tray.pot \
    -l fr_FR \
    -o crates/tisvlay-tray/lang/fr/LC_MESSAGES/tisvlay-tray.po
```

Translate the `msgstr ""` lines in each file, then `cargo build` to compile `.mo`s. `just i18n-update` re-runs `msgmerge` against the latest `.pot` so the per-locale `.po` picks up new strings (marked `fuzzy` until reviewed) and obsoletes removed ones.

## What to translate vs not

- **Translate**: button labels, pane headers, status text, menu items, tooltip copy, helper copy, error messages.
- **Don't translate**: brand names (`"TisVlay"`, vendor names like `"LG WebOS"`), machine identifiers (`"awaiting_tv"`, `"lg"`, `"system-shutdown"`), Unicode glyphs (`"●"`, `"·"`, `"—"`, `"↻"`, `"►"`), technical placeholders (`"192.168.1.100"`, `"AA:BB:CC:DD:EE:FF"`), font-family CSS values, file paths, URLs.
- **Brand inside composite templates**: when "TisVlay" is bracketed with translatable status (`"TisVlay [daemon offline]"`, `"TisVlay [{0}/{1}]"`), wrap the whole template — translators pass the brand through verbatim.

### Format-string idiom

`xgettext` extracts string literals passed as the first argument to a keyword call (`gettext`, `ngettext`). It cannot recover the literal from a `format!(…)` argument because the macro consumes it before extraction. To keep formatted strings extractable:

```rust
// Wrong — xgettext sees no literal.
format!("Backlight: {}", bl)

// Right — literal stays a bare argument to gettext.
gettext("Backlight: {0}").replace("{0}", &bl.to_string())
```

Multi-placeholder strings chain `.replace`:

```rust
gettext("TisVlay [{0}/{1}]")
    .replace("{0}", &connected.to_string())
    .replace("{1}", &total.to_string())
```

## Decision rationale

### Why gettext-rs (vs Fluent, i18n-embed, rust-i18n)

**Mozilla Fluent (via `fluent-rs`).** Has real ergonomic wins over gettext for translator-visible features: locale-correct plurals via `intl_pluralrules`, message references and terms, attributes (one ID carries `.label` / `.tooltip` / `.aria-label` as a unit), BiDi isolation by default, non-fatal error handling, runtime catalog reload. Rejected because:

- **No extractor exists in the Fluent ecosystem** — you hand-write `.ftl` and keep IDs in sync with code yourself. The workspace gets free extraction via `slint-tr-extractor` + `xgettext`; that gap matters.
- Translator-tool support is weaker — Pontoon is strong, Poedit / Weblate / Crowdin / Transifex / Lokalize are weak or missing for `.ftl`.
- `fluent-fallback`'s own README warns the API is *"in the early stages"* and asks consumers to *"work through the challenge of setting up the boiler-plate that will eventually go away."*
- At the workspace's current scale (<100 user-facing strings total), Fluent's selector / attribute / reference power doesn't pay back the tooling-gap cost. The crossover point is roughly when string complexity (plurals, gender, attributes per element) outgrows what `msgctxt` + `ngettext` handle.

**Slint forces gettext for `.slint` files** anyway (see [the Slint blog post](https://slint.dev/blog/translation-infrastructure) and slint-ui/slint#33). The original-English-string-in-source design is load-bearing for Slint's UI-author workflow and isn't going to change. So the GUI is locked into gettext at the `.slint` authoring layer regardless of what the runtime resolver does.

**`i18n-embed` with the gettext backend.** Thin framework wrapper that uses `RustEmbed` to bundle `.mo` files into the binary at build time, plus an `i18n.toml` config that automates `msgmerge` / `msgfmt`. Same `.po`/`.pot` source files; different runtime loader. Rejected because:

- It would diverge the tray (`i18n-embed`-wrapped) from the GUI (`gettext-rs` raw) — the symmetry argument we're choosing gettext-rs for in the first place.
- The build-script complexity it eliminates (`msgfmt` shell-out) is ~15 lines.
- Modestly maintained — last meaningful release Nov 2023.

Revisit only if/when both crates want compile-time-embedded `.mo` files rather than system-installed.

**`rust-i18n`.** YAML/JSON catalogs, no proper plural rules, no `msgctxt` equivalent. Closer to a toy than a serious i18n stack. Not considered further.

### Why a build.rs vs checking in `.mo` files

The GUI gets `.mo` compilation for free from `slint_build::compile("ui/main.slint")` — Slint's `gettext` feature config triggers `msgfmt` as a side effect. The tray has no Slint dependency, so something else has to run `msgfmt`. Two options:

- **`build.rs` + `msgfmt`** (chosen). Idiomatic Cargo pattern, `.mo` regenerates automatically on `.po` change, `target/`-only artifact, no churn in `git status`. Failure mode: `cargo:warning=` and degrade (runtime falls back to source strings), never fail the build — mirrors the GUI's `cargo-about` fallback in [crates/tisvlay-gui/build.rs](../crates/tisvlay-gui/build.rs).
- **Check in `.mo` alongside `.po`.** Zero build complexity, runtime can `include_bytes!` directly. Cost: every `.po` edit produces two diffs; binary blobs in `git`; translators have to remember to recompile or wire a pre-commit hook.

### Why `bindtextdomain` directly vs `gettextrs::TextDomain`

`gettextrs::TextDomain::new("…").init()` is the higher-level API but its lookup logic walks XDG paths only — dev runs out of the source tree miss the `lang/` directory entirely. The lower-level `bindtextdomain` + `textdomain` pair (the same primitives `slint::init_translations!` calls under the hood) lets the binary point at `CARGO_MANIFEST_DIR/lang` baked at compile time, so `cargo run` and `target/debug/tisvlay-tray` resolve catalogs against the in-tree directory the build script populates. Installed builds with no catalog at the baked path silently fall back to source strings — a known v1 limitation, fixed properly when packaging adds `/usr/share/locale/<locale>/LC_MESSAGES/<domain>.mo` install steps and the binaries learn to consult that path.

### Slint external-translator escape hatch

`slint::SlintContext::set_external_translator` (added via LibrePCB's PR slint-ui/slint#10979) routes Slint's `@tr()` resolution through a user-supplied callback. If the workspace ever decides to adopt Fluent end-to-end, both the tray and the GUI can move together — the `.slint` authoring surface stays gettext-shaped (English source strings, no message IDs), but the runtime resolver delegates to Fluent. **No lock-in is created by adopting gettext-rs now.** The crossover trigger would be string-complexity growth (plurals, gender, message references, BiDi) that outgrows gettext's `msgctxt` + `ngettext` toolkit, not a tooling shift.
