# Promo video

## Goal

One set of declarative, reproducible sources under `docs/promo/` that renders three cuts of a TisVlay demo video:

- **Hero loop:** 10–15 s, silent, 16:9, for the top of the README and the book's landing page. Just the beat, lock → screen off, unlock → screen on, with a small wordmark in a corner and no cards: it sits under the README banner, and cards at the loop seam would be half of it.
- **Release clip:** about 60 s, narrated, with captions burned in for muted autoplay. Re-rendered per release with the version on the end card.
- **Walkthrough:** 6–7 min, narrated, chaptered, in three acts: a day in the life, a feature tour of every group under the README's Features, then a setup tutorial. Each act also renders as its own video, so the book's Getting Started can link the setup tutorial directly.

Every narrated cut opens on the title card and pitch. The audience is layered: the opening speaks to the Linux user whose display is a TV, widens to the couch and HTPC gamer, and ends on the hooks for tinkerers and developers.

The cuts share their shots. A shot is written once, and each cut is a list of shots plus timing. Every input is either checked in (shot HTML, scripts, narration text, VHS tapes) or regenerated by a script from the code (UI captures, timelines, narration audio). Re-rendering after a UI change means running one recipe, not re-editing a video.

## Decisions

- **Composition: [HyperFrames](https://github.com/heygen-com/hyperframes).** Scenes are plain HTML/CSS with data-attribute timing. Rendering seeks each frame in headless Chrome and encodes it with FFmpeg, so the same input gives the same output. Apache-2.0, unlike Remotion's source-available license that depends on company size. Claude Code skills ship with it. Risk: the project dates from spring 2026, so step 1 proves it on NixOS before anything depends on it.
- **The TV is animated, driven by real data.** The TV's own screen (going dark, the volume overlay) isn't in the PC's HDMI output, so it can't be screen-captured. A stylized TV component in the composition replays a timeline recorded from a scripted run of the real stack. No camera, no real TV.
- **One timeline per shot.** The driver writes a single JSONL timeline: its own actions (lock, wake, a remote press), the stack's published state (what `tisvlay watch` shows), what the logind fake observed (a lock or sleep request), and the start and step marks of any GUI clip. The watch stream alone can't say "the PC locked" or "the PC went to sleep", and the clips need the same clock to line up.
- **Timing: real inside a beat, retimed between beats.** Event order and the latency inside a beat (lock → screen off) are the stack's own. The gaps between beats stretch or shrink to fit the narration.
- **Illustrated beats are marked.** Where the stack has nothing to record (the desktop reacting to remote keys, the approval prompt on the TV), the shot is an illustration triggered by a timeline event, and the storyboard says so.
- **A real daemon, with the mock connector posing as the vendors.** The driver boots the real daemon and session in-process, the way the wire tests do, and registers the mock connector under the real vendor ids and names with their real capability sets (`serve` takes the vendor registrations). The world, systems, profiles and wire are all real; only the backend is fake. The GUI then shows real vendor names, and the driver holds the `MockHandle`, which is the only way to publish a discovered TV, accept a pairing, press the remote's power key or cut a link. The real C3/G4 are never touched, and pox's display (the TV) stays out of the run. Not zenoh spoofing (it would have to fake liveliness, the release handshake and every queryable, and could show states the stack never produces) and not the Bevy Remote Protocol (the world is `bevy_ecs` alone, so it would add `bevy_app`, reflection and a network listener to the product, and bypass the systems).
- **Shot scripts are data.** One TOML file per shot under `docs/promo/shots/`: a list of steps (`lock`, wait for a state, set a value, a `MockHandle` call). The driver is a small interpreter, so a storyboard change is a diff to a data file, not a Rust edit.
- **The demo household is two TVs.** "Desk", a network TV, carries the day in the life. "Living Room", an HDMI-CEC TV, carries the couch and multi-vendor shots. Their addresses and identifiers are invented.
- **Art style: flat and Breeze-toned.** Flat vector shapes in the GUI's Breeze Dark palette and accent color, so captures and illustration read as one product. Picked over a blocky, warm style taken from the banner.
- **The TV's standby light sits bottom center** and is lit only in standby (TV powered off). A screen that is merely off shows a dark panel and no light, so the two states read differently.
- **A small PC stands beside the TV,** a simple tower with a power light, joined to the TV by a line that pulses when a command crosses: solid for the network, a second style for HDMI-CEC. It shows cause and effect, and the PC's own lock, sleep and wake.
- **Short state chips, one caption per beat.** Each device carries a chip for its state ("screen off", "locked"), and each beat one short caption, so the silent loop reads without narration.
- **The animated TV shows an abstract desktop** while it is on: a panel, blank windows and a wallpaper gradient, brand-free and clearly an illustration.
- **Lock, sleep and idle are injected.** The driver hosts `tisvlay-test`'s private bus and `FakeLogind` (`set_locked`, `emit_prepare_for_sleep`) and hands the stack that connection, as the session and daemon tests do. Idle goes through the session's idle adapter the same way: no real timeout, no synthetic pointer.
- **Bare windows, framed.** The GUI and CLI are the only subprocesses. The GUI is captured alone in a headless wlroots compositor at 1920×1080 with `wf-recorder`, driven step by step over the Slint MCP server on its own port (not the dev GUI's). The composition places it on a branded background taken from `docs/artwork/`. The tray menu is an overlay built on the real tray screenshot (`docs/screenshots/`) with animated highlights, not captured live, because it needs a Plasma panel, and not redrawn in HTML, which would drift.
- **Dark theme only, through a fake portal.** It fits the OLED / living-room story. The GUI has no theme override by design (`theme.slint` follows the portal's color scheme), so the driver serves a small fake `org.freedesktop.portal.Settings` on its private session bus, answering dark and a fixed accent color. No product code changes.
- **Couch mode is captured with `TISVLAY_COUCH_MODE`** (the existing override in `crates/tisvlay-gui-app/src/couch.rs`). The keys reach the GUI as key events over MCP; the remote or gamepad drawn beside it is an illustration timed to those steps.
- **CLI shots are VHS tapes** (`.tape` files, `vhs` in nixpkgs), run against the same dev stack.
- **No music.** Narration only, with UI sound effects at most: nothing to license or credit.
- **Three narration tones, screened on the release clip.** The release clip's narration and on-screen text, the title card's pitch line included, is written in three variants: *calm* (short declarative lines, like the docs), *warm* (brief, lightly playful), and *technical* (names the mechanisms: logind, DPMS, HDMI-CEC, the network protocol). The tone is a render parameter. After the screening, the losing variants are deleted and the walkthrough is written only in the winner.
- **The storyboard tells the default profiles' story.** Each beat shows what the shipped defaults do. Where a beat needs a non-default choice (TV-drives-PC, input gating), the shot shows the profile change first, which doubles as the profiles pitch. The defaults are read from the generated partials (`docs/book/src/generated/profile-defaults-*.md`), not restated here.
- **Narration: Kokoro-FastAPI** (OpenAI-compatible, `/v1/audio/speech`). Its `/dev/captioned_speech` endpoint returns word timestamps, so shot timing and burned-in captions come from the TTS call itself, with no separate alignment pass. Voice: `af_heart`, chosen from rendered samples of eight voices and blends. The service runs on pox, not in the flake, so the endpoint is a recipe variable and the generated audio is cached per narration line (keyed by text + voice), so a re-render on the same machine needs no Kokoro instance. The cache is gitignored, so a fresh clone needs one.
- **Outputs are release assets, never committed, and rendered locally.** `docs/promo/out/` and every intermediate (captures, timelines, audio cache, `node_modules`) are gitignored. A release render needs a compositor and the narration cache, so it is a local step in the release checklist, like the bump. Rendered files are uploaded to the GitHub release, and the README and book link to them.
- **The toolchain is a second shell in the root flake.** `devShells.promo` holds Node, Chromium, FFmpeg, VHS, the compositor and `wf-recorder`: one lockfile and one nixpkgs pin, and the default shell and the package build never evaluate it. Recipes live in the root `justfile` under a `promo` group (the justfile is the single source of commands) and call `nix develop .#promo -c …`. No CI gate renders video. Lint gates that walk `docs/` (typos, file checks) still apply to the sources.

## Steps

Each step is one commit, and the plan is committed first as the baseline.

1. **Toolchain.** `devShells.promo` in the root flake, `docs/promo/package.json` + lockfile pinning HyperFrames, `.gitignore`, and `promo-*` recipes in the root `justfile`. Point HyperFrames at nixpkgs Chromium. Verify: a test composition with HTML animation, an embedded video clip and an audio track renders to MP4 from `just promo-render`; the clip's frames land on the right composition frames (a burned-in frame counter, read back from stills); and rendering twice gives the same frames (hash a sample).
2. **Driver.** An example in `tisvlay-session` (its dev-dependencies already hold the daemon and the mock; nothing joins the normal build). It boots the daemon and session in-process on temp sockets with the mock connector under the real vendor registrations, hosts the private bus with `FakeLogind` and the fake portal Settings, plays a shot's script (wake, lock, unlock, idle, sleep, setters, stream start/end, profile changes, `MockHandle` calls), and writes the timeline as JSONL. Verify: two runs produce the same event sequence. Timestamps may differ; the composition normalizes them.
3. **Animated TV component.** HTML/CSS TV whose state (power, screen, volume, input, link) is a function of the timeline at time *t*. Verify: rendered stills at chosen times match the expected state; Claude reads the frames.
4. **GUI capture.** The driver starts the GUI in the headless compositor against its sockets and private buses, records it with `wf-recorder`, drives it over MCP, and marks each step in the timeline. Settles the compositor (`cage`, or sway headless if the output size can't be set) and software rendering. Verify: captured clips for shots 1.2, 1.7 and 3.2, dark and at 1920×1080, frame-checked.
5. **CLI capture.** VHS tapes for shots 2.4 and 2.5 against the driver's stack. Verify: the tapes render, and their output matches the live CLI.
6. **Narration.** `docs/promo/narration/<tone>/*.md` for the release clip's shots (one line per sentence, per shot, one directory per tone) → Kokoro captioned speech → audio + word timings, cached. Gaps between beats stretch to the narration. Captions are rendered from the timings. Verify: an audio/caption sync check on shot 1.3 in each tone.
7. **Release clip and screening.** The release clip's shots, the hero loop, and the clip rendered in all three tones. Verify: the user screens them and picks a tone; the other variants are deleted.
8. **Walkthrough.** The remaining shots and narration in the chosen tone, the walkthrough and the three act cuts. Verify: every cut renders; the user reviews them.
9. **Release hookup.** A recipe that renders the cuts and uploads them to a release with `gh release upload`. Add the README/book links and a local step in packaging/README.md § Release checklist. Verify: a dry run against a draft release.
10. **Retire the plan.** Fold the durable parts (pipeline, re-render workflow, decisions) into `docs/promo/README.md`, put leftovers in `docs/ideas/`, and delete this file.

## Open questions

- **Hosting and README embedding:** decided after the cuts are edited, by comparing quality and visitor experience: release assets only or a YouTube/PeerTube mirror; an animated WebP via `<img>`, a `user-attachments` MP4, or a poster that links out.
- **Vendor-specific pairing fields:** whether the wizard under a posed vendor registration shows that vendor's real pairing form (shot 3.3), or the mock's. Settled in step 2.

## Deviations

- **Step 1:** nixpkgs Chromium lacks the headless-shell frame API HyperFrames prefers, so it captures in its screenshot mode. Two renders still match frame for frame, and the embedded clip's frames land on the right composition frames, so the plain browser stays. The typeface is linked from the Nix store by `just promo-setup`, because HyperFrames otherwise fetches a missing family from Google Fonts at render time. Renders run with `--strict`, which caught an audio element that would have rendered silent. Still open: a harmless 404 the renderer logs per worker, and its "no index.html" notice, which goes away once the cuts get a project index.
