# Promo video

## Goal

One set of declarative, reproducible sources under `docs/promo/` that renders three cuts of a TisVlay demo video:

- **Hero loop:** 20–40 s, silent, 16:9 WebM, for the top of the README and the book's landing page. Title card, then lock → screen off, unlock → screen on.
- **Release clip:** about 60 s, narrated, with captions burned in for muted autoplay. Re-rendered per release with the version on the end card.
- **Walkthrough:** 6–7 min, narrated, chaptered, in three acts: a day in the life, a feature tour of every group under the README's Features, then a setup tutorial.

Every cut opens on the title card and pitch. The audience is layered: the opening speaks to the Linux user whose display is a TV, widens to the couch and HTPC gamer, and ends on the hooks for tinkerers and developers.

The cuts share their shots. A shot is written once, and each cut is a list of shots plus timing. Every input is either checked in (scene HTML, scripts, narration text, VHS tapes) or regenerated by a script from the code (UI captures, event logs, narration audio). Re-rendering after a UI change means running one recipe, not re-editing a video.

## Decisions

- **Composition: [HyperFrames](https://github.com/heygen-com/hyperframes).** Scenes are plain HTML/CSS with data-attribute timing. Rendering seeks each frame in headless Chrome and encodes it with FFmpeg, so the same input gives the same output. Apache-2.0, unlike Remotion's source-available license that depends on company size. Claude Code skills ship with it. Risk: the project dates from spring 2026, so step 1 proves it on NixOS before anything depends on it.
- **The TV is animated, driven by real data.** The TV's own screen (going dark, the volume overlay) isn't in the PC's HDMI output, so it can't be screen-captured. A stylized TV component in the composition replays a `tisvlay --json watch` event log recorded from a scripted mock run. The animation shows the stack's real event order and timing, not hand-placed keyframes. No camera, no real TV.
- **The mock backend is the TV.** It advertises the stock capabilities plus remote power, remote keys and wakes-PC (`crates/tisvlay-mock/src/backend.rs`), which covers every feature the video shows. The real C3/G4 are never touched, and pox's display (the TV) stays out of the run.
- **Lock, sleep and idle come from fakes, not the desktop.** A driver hosts a private `dbus-daemon` and `tisvlay-test`'s `FakeLogind` (`set_locked`, `emit_prepare_for_sleep`) and points the session at it through `DBUS_SYSTEM_BUS_ADDRESS`. Idle is real: the session's ext-idle-notify client runs inside the same headless compositor as the GUI.
- **Bare windows, framed.** The GUI is captured alone in a headless wlroots compositor (`cage`, at 1920×1080) with `wf-recorder`, driven step by step over the Slint MCP server (`SLINT_MCP_PORT`). The composition places it on a branded background taken from `docs/artwork/`. The tray menu is recreated as a styled HTML overlay, not captured, because it needs a Plasma panel.
- **Dark theme only.** It fits the OLED / living-room story. How the GUI is forced dark under `cage` (no portal, no Plasma colors) is checked in step 4. If no knob exists, the fallback is an environment override, not a new product option.
- **Couch mode is captured with `TISVLAY_COUCH_MODE`** (the existing override in `crates/tisvlay-gui-app/src/couch.rs`). Remote and gamepad presses are animated, driven by the same event log.
- **CLI shots are VHS tapes** (`.tape` files, `vhs` in nixpkgs), run against the same dev stack.
- **No music.** Narration only, with UI sound effects at most: nothing to license or credit.
- **Three narration tones, screened before one is picked.** Each shot's narration and on-screen text, the title card's pitch line included, exists in three variants: *calm* (short declarative lines, like the docs), *warm* (brief, lightly playful), and *technical* (names the mechanisms: logind, DPMS, HDMI-CEC, the network protocol). The tone is a render parameter, so each cut renders once per tone for test screenings. After the pick, the losing variants are deleted, not kept.
- **The storyboard tells the default profiles' story.** Each beat shows what the shipped defaults do. Where a beat needs a non-default choice (TV-drives-PC, input gating), the shot shows the profile change first, which doubles as the profiles pitch. The defaults are read from the generated partials (`docs/book/src/generated/profile-defaults-*.md`), not restated here.
- **Narration: Kokoro-FastAPI** (OpenAI-compatible, `/v1/audio/speech`). Its `/dev/captioned_speech` endpoint returns word timestamps, so shot timing and burned-in captions come from the TTS call itself, with no separate alignment pass. Voice: `af_heart`, chosen from rendered samples of eight voices and blends. The service runs on pox, not in the flake, so the endpoint is a recipe variable and the generated audio is cached per narration line (keyed by text + voice), so a re-render without a Kokoro instance reuses it.
- **Outputs are release assets, never committed.** `docs/promo/out/` and every intermediate (captures, logs, audio cache, `node_modules`) are gitignored. Rendered files are uploaded to the GitHub release, and the README and book link to them.
- **The toolchain stays out of the main dev shell.** `docs/promo/flake.nix` holds Node, Chromium, FFmpeg, VHS, `cage` and `wf-recorder`. Recipes live in the root `justfile` under a `promo` group (the justfile is the single source of commands) and call `nix develop ./docs/promo -c …`. No CI gate renders video. Lint gates that walk `docs/` (typos, file checks) still apply to the sources.

### Cuts

- **Hero loop:** T (short) → 1.3 → E (short), with a seamless loop seam.
- **Release clip:** T → 1.3 → 1.2 → 1.5 → 1.7 → 3.2–3.3 (fast) → E. Evergreen: only the version on the end card changes per release, with no "what's new" segment.

## Steps

Each step is one commit, and the plan is committed first as the baseline.

1. **Toolchain.** `docs/promo/flake.nix` + lockfile, `package.json` + lockfile pinning HyperFrames, `.gitignore`, and `promo-*` recipes in the root `justfile`. Point HyperFrames at nixpkgs Chromium. Verify: a hello scene renders to MP4 from `just promo-render`, and rendering it twice gives the same frames (hash a sample of frames).
2. **Event-log driver.** A dev-only driver (a `tisvlay-test` example, never published) that starts the daemon, session and GUI on temp sockets with the mock backend inside `cage`, hosts the private bus with `FakeLogind`, plays a shot's script (wake, lock, unlock, idle, sleep, CLI setters, stream start/end, profile changes), and writes `tisvlay --json watch` output as JSONL with timestamps. Verify: two runs produce the same event sequence. Timestamps may differ; the composition normalizes them.
3. **Animated TV component.** HTML/CSS TV whose state (power, screen, volume, input, link) is a function of the event log at time *t*. Verify: rendered stills at chosen times match the expected state; Claude reads the frames.
4. **GUI capture.** `cage` + `wf-recorder` + MCP-driven step scripts, dark theme settled, couch mode via the environment override. Verify: captured clips for shots 1.2, 1.7 and 3.2, frame-checked.
5. **CLI capture.** VHS tapes for shots 2.4 and 2.5 against the driver's stack. Verify: the tapes render, and their output matches the live CLI.
6. **Narration.** `docs/promo/narration/<tone>/*.md` (one line per sentence, per shot, one directory per tone) → Kokoro captioned speech → audio + word timings, cached. Shot durations stretch to the narration. Captions are rendered from the timings. Verify: an audio/caption sync check on shot 1.3 in each tone.
7. **Shots and cuts.** Every shot in the storyboard and the three cut definitions. Verify: each cut renders in all three tones for the test screenings; the user screens them, picks a tone, and the other variants are deleted.
8. **Release hookup.** A recipe that renders the cuts and uploads them to a release with `gh release upload`. Add the README/book links and a step in packaging/README.md § Release checklist. Verify: a dry run against a draft release.
9. **Retire the plan.** Fold the durable parts (pipeline, re-render workflow, decisions) into `docs/promo/README.md`, put leftovers in `docs/ideas/`, and delete this file.

## Open questions

- **Hosting and README embedding:** decided after the cuts are edited, by comparing quality and visitor experience: release assets only or a YouTube/PeerTube mirror; an animated WebP via `<img>`, a `user-attachments` MP4, or a poster that links out.
- **A link drop for 2.6:** reuse the seam the outage and redial tests already use (in the mock or `tisvlay-test`); add a dev-only mock knob only if none fits. Settled in step 2.
