# Advertise our OSD name: label the TV's HDMI input like a Chromecast

Status: **proposed** (baseline for review; not yet implemented).

## Problem

A CEC source device tells the TV what to call its HDMI input by answering the TV's `<Give OSD Name>` poll with `<Set OSD Name>` (opcode `0x47`) — this is exactly how a Chromecast makes its input read "Chromecast". TisVlay already presents the on-bus profile a streaming stick does: it claims a **Playback** logical address (`LinuxCecLink::open` → `set_logical_address(LogicalAddressType::Playback)`) at a physical address matching the port, and it already *reads* the TV's own OSD name to build the cross-vendor `HardwareId` (`CecLink::query_osd_name`, `identity::query`). What it never does is advertise a name for *itself*, so the TV falls back to a generic/driver-default label for the PC's input. The feature is the missing mirror of the identity read: we ask the TV "what are you called?" but never answer "what are we called?"

## Design

The headline is mechanism *absence*: advertise our identity as part of the adapter's log-address configuration and the Linux CEC core answers the TV for us — no bespoke responder, no message pump on the monitor fd.

The Linux CEC framework, when a fd is a plain follower (not exclusive or passthrough), auto-replies to `<Give OSD Name>` and `<Give Device Vendor ID>` straight from the adapter's configured `cec_log_addrs`. TisVlay's monitor handle already runs plain `CEC_MODE_FOLLOWER` (`FollowerMode::Enabled` → `CecFollowerModes::Follower`), the mode that leaves in-kernel processing intact — only `ExclusiveFollowerPassthru` bypasses it — so nothing we do today suppresses that auto-reply. The whole feature therefore reduces to one rule: **write `osd_name` (and, optionally, the vendor OUI) into the log-addrs config *before* claiming the logical address.** The pinned `linux-cec` 0.2.0 (crates.io, no `[patch]`) exposes exactly this as `AsyncDevice::set_osd_name` / `set_vendor_id` — both `&self` relays that slot into the existing `open` sequence. The library's own doc rule, "call before `set_logical_addresses`", is the tell that the kernel snapshots the name into its per-adapter config at the `S_LOG_ADDRS` ioctl: set it after and the userspace buffer updates but the kernel keeps auto-answering the stale (empty) value.

- **The name describes the PC, not the TV.** The OSD name is what the *source* calls itself, rendered by the TV as the input label — so semantically it is "what to call this machine on the TV" (`HTPC`, `Living Room PC`, a hostname), the reverse direction from the TV-identity read that populates Make/Model. It is a *fact* about how this host presents on the bus, so it lives in device config, not a profile: a new `osd_name: Option<String>` under `[tv.cec]`, beside `device` / `physical_address` / `emulate_screen_via_power`. Per-TV rather than global because a host with two adapters may want a different label on each ("HTPC" in the den, "Office PC" upstairs); a single-adapter host just sets one. **Default `None` = today's behavior exactly** — no name is advertised, the adapter joins the bus as it does now. That zero-delta default is deliberate: it keeps the change inert for every already-paired CEC TV through the PR soak, and makes the feature strictly opt-in.

- **Set it before the logical-address claim; the wake broadcast does the rest.** The insertion point is `LinuxCecLink::open`, unconditionally between the physical-address write and `set_logical_address(Playback)`:

  ```
  set_initiator_mode(Enabled)
  [if PHYS_ADDR cap] set_physical_address(pa)
  if let Some(name) = clamp(osd_name)  { set_osd_name(name) }   // buffer-only: still Unregistered, no tx
  if let Some(v)    = vendor_id        { set_vendor_id(Some(v)) }
  set_logical_address(Playback)                                  // S_LOG_ADDRS submits name+vendor → auto-reply armed
  ```

  Called while the address is still `Unregistered`, `set_osd_name` only writes the local `cec_log_addrs` buffer (it transmits `<Set OSD Name>` *only* once a logical address is claimed) — so there is no stray frame before we are on the bus, and the name rides the same `S_LOG_ADDRS` that claims Playback. No explicit push is needed: the wake path already broadcasts `<Active Source>`, which is precisely what makes a TV poll the newly-active source for its name, so the label surfaces on the next wake through the kernel auto-reply. Unconditional (not gated on the `PHYS_ADDR` cap) because both a USB adapter and a GPU DisplayPort-CEC output benefit from a name; the cap only governs the *physical*-address write.

- **Clamp to 14 bytes of ASCII in the backend, never in the library.** `set_osd_name` rejects a name over 14 bytes with `Error::OutOfRange` (the CEC OSD-name operand is 14 bytes, spec-defined ASCII). A user's friendly label can easily exceed that, and an over-long name must never fail `open` and drag down the whole connection — so tisvlay-cec clamps: reuse `identity::sanitize` to strip control characters (the same NUL/embedded-control hazard the read path already guards), then truncate to 14 bytes on a UTF-8 char boundary, and pass only the clamped value down. Truncation is best-effort and silent; the pairing helper text sets the 14-character expectation up front. (Non-ASCII bytes are passed through post-sanitize — some TVs render UTF-8, most do not; that is a TV-side lottery we neither promise nor prevent.)

- **Optional second lever — claim a vendor OUI for the SIMPLINK icon, off by default and honestly.** Some TVs (LG SIMPLINK among them) key the input's *icon*/branding on the source's reported vendor OUI via `<Give Device Vendor ID>`; a Chromecast reports Google's OUI to get its badge. The same `open`-time hook can call `set_vendor_id`, fed by a new `vendor_oui: Option<String>` (`"00-1a-11"` form, parsed into `linux_cec::VendorId([u8; 3])`). **But TisVlay owns no registered OUI**, so any value it claims is another vendor's identity — impersonation that can also confuse a TV's own SIMPLINK device handling. So this ships *off* (`None` → today's behavior, no vendor advertised), documented as an expert knob with that caveat stated plainly, not a default. It is carried in this plan because it is the same one-line `open` hook and the same config/schema plumbing as the name; whether it ships at all is an explicit review decision (see Open decisions).

- **No capability, no client change.** Advertising a name is passive self-identification, not a control the user invokes — it adds no `Capabilities` bit, changes no client gating, touches no power/screen/input path. The capability table in `docs/cec/protocol.md` is unchanged; this is purely how the adapter presents when it joins the bus. Stating the boundary so the review scopes accordingly.

- **Discovery stays anonymous.** `CecDiscovery` opens each `/dev/cecN` only to probe the TV's identity and closes — a transient scan should not momentarily claim a name on every node it touches, so the discovery open passes no identity (its behavior is unchanged). Only the connection-holding opens (`connect`, `wake_and_connect`) — the ones live while the TV is on and looking — advertise.

## Implementation sketch

1. **`config.rs`**: add `osd_name: Option<String>` (and, if kept, `vendor_oui: Option<String>`) to `CecVendorConfig`, each `#[serde(default)]` = `None`; extend the TOML round-trip and default tests. No new `default_*` fn needed for an `Option` that defaults to `None`.
2. **`link.rs`**: widen the `CecLinkOpener::open` seam to carry what the adapter advertises. Prefer a small `struct AdvertisedIdentity { osd_name: Option<String>, vendor_id: Option<VendorId> }` (one param, extensible) over two positional args next to `physical_address`. In `LinuxCecLink::open`, insert the `set_osd_name` / `set_vendor_id` calls per the recipe above, with a private `clamp_osd_name(&str) -> String` (sanitize + 14-byte truncate). Teach `FakeCecLink` / `FakeCecLinkOpener` to *record* the advertised identity so tests can assert it, and default it empty so existing tests are untouched.
3. **`connector.rs`**: build the `AdvertisedIdentity` from the parsed config and pass it at the connection-holding open sites (`connect`, and both opens in `wake_and_connect`); pass an empty identity from the bare `wake` and from `discovery.rs`'s probe. Add the `osd_name` field (and `vendor_oui` if kept) to `config_schema()` with `required: false` and helper text that states the 14-character limit and the "names this PC on the TV" intent; update the `config_schema_exposes_*` length assertion.
4. **Tests**: (a) an `open` through the fake advertises the configured name/vendor and a `None` config advertises nothing; (b) `clamp_osd_name` unit cases — under/at/over 14 bytes, embedded NUL/control, a multi-byte char straddling the 14th byte; (c) config TOML round-trip incl. absent = `None`; (d) schema exposure. No daemon/world change, so no wire-level test moves.
5. **Docs**: extend `docs/cec/protocol.md` §"Device identity" with a short "Advertising our own name" subsection (the read/answer symmetry, the before-claim rule, the 14-byte clamp, the vendor-OUI caveat); leave a Quirks stub for the field result.

## Non-goals / Open decisions

- **Default source of the name.** Ship `osd_name` defaulting to `None` (opt-in, zero-delta) for v1. Auto-deriving a default from the system hostname (Chromecast-style zero-config) is attractive but pulls a hostname read + its own ASCII/length messiness into the daemon path; propose it as a later GUI-side *prefill* (the pairing wizard suggests the hostname, the user accepts/edits) rather than a daemon default. Flagged for the review pass.
- **Whether the vendor-OUI lever ships at all.** The impersonation caveat is real; the options are (a) ship it off-by-default as an expert knob, or (b) drop it from this PR and file it under `docs/ideas/`. Recommend (a) only if a field test shows it meaningfully improves the icon on the target LGs; otherwise (b). Decision belongs to the review pass + field result.
- **No dynamic rename.** The name is fixed at `open`; a config edit takes effect on the next reconnect, matching how `physical_address` / `emulate_screen_via_power` already behave. No live `<Set OSD Name>` push on config-patch.
- **No new capability, client gating, or power/screen/input behavior change.**
