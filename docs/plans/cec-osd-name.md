# Advertise our OSD name: label the TV's HDMI input like a Chromecast

Status: **round-2 redesign implemented** on PR #114 (needs a GUI re-QA of the clear/toggle flows). History: baseline `a538ea4` → review round `ff27c91` → v1 implemented `4e1c2cf` → field-confirmed on the LG (2026-07-18) → default flipped `None` → `"TisVlay"` (`b9c6e647`). QA then found the documented empty-string opt-out unreachable through both GUI forms, and a max-effort review confirmed the config shape itself was wrong — see § Round 2 redesign, which supersedes the "default `None` / zero-delta" prose and the "empty string opts out" mechanism below (kept for history). Listed until the PR merges.

## Problem

A CEC source device tells the TV what to call its HDMI input by answering the TV's `<Give OSD Name>` poll with `<Set OSD Name>` (opcode `0x47`) — this is exactly how a Chromecast makes its input read "Chromecast". TisVlay already presents the on-bus profile a streaming stick does: it claims a **Playback** logical address (`LinuxCecLink::open` → `set_logical_address(LogicalAddressType::Playback)`) at a physical address matching the port, and it already *reads* the TV's own OSD name to build the cross-vendor `HardwareId` (`CecLink::query_osd_name`, `identity::query`). What it never does is advertise a name for *itself*, so the TV falls back to a generic/driver-default label for the PC's input. The feature is the missing mirror of the identity read: we ask the TV "what are you called?" but never answer "what are we called?"

## Design

The headline is mechanism *absence*: advertise our identity as part of the adapter's log-address configuration and let the in-kernel CEC core answer the TV for us — no bespoke responder, no message pump on the monitor fd.

**Load-bearing assumption (confirm on hardware): the in-kernel CEC core auto-answers `<Give OSD Name>` from the adapter's configured `cec_log_addrs`.** This is Linux CEC *framework* behavior, not something the `linux-cec` crate implements, so the plan treats it as the one thing to verify on real hardware. What we can state precisely: the auto-reply is *adapter-level*, gated on the configured `osd_name` being non-empty and on no fd holding the traffic via exclusive-follower/passthrough — it would fire even with no follower fd open at all. TisVlay's monitor handle runs plain `CEC_MODE_FOLLOWER` (`FollowerMode::Enabled` → `CecFollowerModes::Follower`, the mode that leaves in-kernel processing intact — only `ExclusiveFollowerPassthru` bypasses it), so it does not *suppress* the auto-reply; it is not what *arms* it. The name is armed by the *tx* link, which submits `osd_name` in its `S_LOG_ADDRS` claim. The corollary is a free correctness proof of the default: an empty `osd_name` means the kernel sends no reply, so `None` reproduces today's behavior byte-for-byte.

The whole feature therefore reduces to one rule: **write `osd_name` into the log-addrs config *before* claiming the logical address.** The pinned `linux-cec` 0.2.0 (crates.io, no `[patch]`) exposes exactly this as `AsyncDevice::set_osd_name`, a `&self` relay that slots into the existing `open` sequence. The library's own doc rule, "call before `set_logical_addresses`", is the tell that the kernel snapshots the name into its per-adapter config at the `S_LOG_ADDRS` ioctl: set it after and the userspace buffer updates but the kernel keeps auto-answering the stale (empty) value.

- **The name describes the PC, not the TV.** The OSD name is what the *source* calls itself, rendered by the TV as the input label — semantically "the name this adapter advertises for itself on a given TV input", the reverse direction from the TV-identity read that populates Make/Model. It is a *fact* about how this host presents on the bus, so it lives in device config, not a profile: a new `osd_name: Option<String>` under `[tv.cec]`, beside `device` / `physical_address` / `emulate_screen_via_power`. It is stored per paired-TV because that is the config granularity that exists (there is no per-host CEC layer), which conveniently lets a host with two adapters differentiate them ("HTPC" in the den, "Office PC" upstairs) while a single-adapter host just sets one. **Default `None` = today's behavior exactly** — no name is advertised, the kernel stays silent on the poll, the adapter joins the bus as it does now. That zero-delta default is deliberate: it keeps the change inert for every already-paired CEC TV through the PR soak, and makes the feature strictly opt-in.

- **Set it before the logical-address claim; the wake broadcast does the rest.** The insertion point is `LinuxCecLink::open`, unconditionally between the physical-address write and `set_logical_address(Playback)`:

  ```
  set_initiator_mode(Enabled)
  [if PHYS_ADDR cap] set_physical_address(pa)
  if let Some(name) = osd_name.and_then(identity::clamp_osd_name) { set_osd_name(&name) }
  set_logical_address(Playback)                     // S_LOG_ADDRS submits osd_name → kernel auto-reply armed
  ```

  On a freshly opened fd the logical address is still `Unregistered`, so `set_osd_name` only writes the local `cec_log_addrs` buffer — it transmits `<Set OSD Name>` *only* once an address is claimed — and the name then rides the same `S_LOG_ADDRS` that claims Playback. (The one exception: if an adapter retained a prior claim across an unclean close, the freshly opened handle reads that address back and `set_osd_name` transmits the frame immediately — harmless, since it is exactly the message we want the TV to receive.) No explicit push is needed in the normal case: the wake path already broadcasts `<Active Source>`, precisely what makes a TV poll the newly-active source for its name, so the label surfaces on the next wake through the kernel auto-reply. **The label rides the open connection** — the tx fd stays open for the connection's life, so `cec_log_addrs` remains configured and the kernel re-answers every re-poll (e.g. after the TV power-cycles) with no daemon action; this is the same wake-in-place persistence the power path already leans on, and the reason the transient opens below correctly advertise nothing. Unconditional (not gated on the `PHYS_ADDR` cap) because both a USB adapter and a GPU DisplayPort-CEC output benefit from a name; the cap only governs the *physical*-address write.

  If the kernel auto-reply proves unreliable in the field, the ready fallback is a **proactive push** — call `set_osd_name` *after* the claim, which the library transmits as `<Set OSD Name>` directly — not a hand-rolled responder on the monitor fd (that would only duplicate in-kernel processing). Naming the fallback here is the de-risk; it is one line, not a subsystem.

- **Clamp to 14 bytes of ASCII, in `identity.rs` beside `sanitize`.** `set_osd_name` rejects a name over 14 bytes with `Error::OutOfRange` (the CEC OSD-name operand is a 14-byte, spec-defined-ASCII field), and that error would fail the whole `connect`. A user's friendly label easily exceeds that, so the clamp is load-bearing. It is the write-mirror of the existing read-side `sanitize`, so it lives next to it: a new `pub(crate) fn clamp_osd_name(&str) -> Option<String>` that strips control characters (the same NUL/embedded-control hazard `sanitize` already guards), truncates to 14 bytes on a UTF-8 char boundary (via stable `is_char_boundary`/`char_indices`, not nightly `floor_char_boundary`), and returns `None` if nothing survives — matching `identity::query`'s own "sanitize then drop-if-empty" shape, so an all-control-character label advertises nothing rather than an empty name. Truncation is silent and best-effort; the pairing helper text sets the 14-character expectation up front. (Non-ASCII bytes survive the sanitize and are passed through — `set_osd_name` validates length, not charset — but whether a TV renders UTF-8 is a TV-side lottery we neither promise nor prevent.)

- **No capability bit, no client *gating* change.** Advertising a name is passive self-identification, not a control the user invokes — it adds no `Capabilities` bit, changes no client capability gating, and touches no power/screen/input path. The pairing/edit form does gain one optional field, but it renders generically from `config_schema` with no client *code* change, and the daemon/world layer is untouched (config crosses as opaque `toml::Value`). The capability table in `docs/cec/protocol.md` is unchanged.

- **Discovery and the bare wake stay anonymous.** `CecDiscovery` opens each `/dev/cecN` only to probe the TV's identity and closes; the bare `wake` opens, sends `Image View On`, and drops. Both are transient and release the logical address before a TV would poll, so neither can meaningfully deliver a name — and a scan certainly should not momentarily claim one on every node it touches. So both pass `None`. Only the connection-holding opens (`connect`, and both opens inside `wake_and_connect`) — the ones live while the TV is on and looking — advertise.

## Implementation sketch (OSD name only)

1. **`config.rs`**: add `#[serde(default, skip_serializing_if = "Option::is_none")] pub osd_name: Option<String>` to `CecVendorConfig` (the LG backend's optional-field pattern; `#[serde(default)]` alone would risk writing a stray empty key). Give it a doc comment that explicitly contrasts "the name **this adapter advertises for itself**" with the TV's own OSD name that `query_osd_name` reads, so the two `osd_name`s don't conflate. Two non-obvious compile fixes ride this, beyond "add a round-trip test": the hand-written `impl Default for CecVendorConfig` must gain `osd_name: None` (it lists every field), and `physical_address_round_trips_through_toml` builds an exhaustive `CecVendorConfig { .. }` literal with no `..Default::default()`, so it won't compile until the field is added there too.
2. **`link.rs`**: widen the `CecLinkOpener::open` seam with a single `osd_name: Option<&str>` param, matching how `physical_address` is already passed positionally (no wrapper struct — there is one field). In `LinuxCecLink::open`, insert the clamped `set_osd_name` per the recipe (calling `identity::clamp_osd_name`). Teach `FakeCecLink` / `FakeCecLinkOpener` to *record* the raw advertised name so tests can assert it, defaulting it absent so existing tests are untouched. `open_monitor` stays un-widened — the monitor claims no address and cannot advertise.
3. **`connector.rs`**: pass `config.osd_name.as_deref()` at the connection-holding open sites (`connect`, and both opens in `wake_and_connect`); pass `None` from the bare `wake` and from `discovery.rs`'s probe. Add the `osd_name` field to `config_schema()` with `required: false`, `default: ""` (an **empty** default is required — `display_rows_for_visibility` elides empty effective values, so this is what keeps both the `display_config` row-count test and the read-only view zero-delta), and `label`/`helper` as plain `.into()` literals with `translation_key` left `None` (matching every existing LG/CEC schema string and `docs/i18n.md`'s deferred-per-vendor-schema stance — do **not** reach for `gettext` here despite CLAUDE.md's generic "translate helper copy" line). Write the helper in American English (the neighboring screen-via-power helper uses British "Fulfil" — don't inherit it) and state the 14-character limit and the "names this PC on the TV" intent. Update the `config_schema_exposes_*` length assertion.
4. **Tests**: (a) an `open` through the fake advertises the configured name, a `None` config advertises nothing, and the **discovery probe and bare `wake` advertise nothing** (locks the anonymity decision now that the fake records it); (b) `clamp_osd_name` unit cases beside the `sanitize` tests — under/at/over 14 bytes, embedded NUL/control, an all-control input → `None`, and a multi-byte char straddling the 14th byte (truncates on the boundary, no panic); (c) config TOML round-trip including absent = `None` and the `skip_serializing_if` (a `None` serializes no key); (d) schema exposure with the new field carrying **no** non-empty default, plus an assertion that a *set* `osd_name` surfaces in `display_config`'s read-only rows (parity with the `emulate_screen_via_power` display regression test). No daemon/world change, so no wire-level test moves.
5. **Docs**: extend `docs/cec/protocol.md` §"Device identity" with an "Advertising our own name" subsection (the read/answer symmetry, the before-claim rule, the kernel-auto-reply assumption, the 14-byte clamp), and widen `identity.rs`'s module doc, currently framed read-only, to cover both directions. Do **not** pre-stub the Quirks table — the convention there is to add a Symptom→Fix row only once field testing surfaces something (the Field verification section below owns that).

## Deferred follow-up: vendor OUI for the SIMPLINK icon

Kept designed but **out of this PR**, gated on the field result. Some TVs (LG SIMPLINK among them) key the input's *icon*/branding on the source's reported vendor OUI via `<Give Device Vendor ID>`; a Chromecast reports Google's OUI to get its badge. The same `open`-time hook could call `AsyncDevice::set_vendor_id(Option<VendorId>)` (present in 0.2.0, always buffer-only — no transmit path), fed by a `[tv.cec].vendor_oui` field. It is deferred for three converging reasons: (1) **TisVlay owns no registered OUI**, so any value it claims is another vendor's identity — impersonation that can also confuse a TV's own SIMPLINK device handling; (2) the ship decision already depends on a field test showing it actually changes the icon on the target LGs, so wiring config + schema + parser + tests before that test is cart-before-horse; (3) it roughly doubles the review surface (a second config field, a second schema field exposing an impersonation knob in the GUI, a caveat paragraph) for uncertain payoff. If a duty-week field test greenlights it, the follow-up adds the field — typed as `Option<VendorId>` so the library's serde `Deserialize` (the `"aa-bb-cc"`, exactly-two-hex-digits-per-octet form; `VendorId` also has `FromStr`) validates at config-parse time rather than failing every `connect` in the hot path — plus the schema entry with its impersonation caveat, and folds `osd_name` + `physical_address` + `vendor_id` into one "what the adapter claims" struct at that point (don't split two-in-a-struct, one-out). Until then it is filed under `docs/ideas/` at merge time, per the plans README migration convention.

## Field verification (pending)

Needs real hardware — the C3/G4 with the Pulse-Eight USB-CEC adapter — and folds into the planned duty week. Isolate the two failure halves rather than treating all uncertainty as TV-side:

- **Baseline first.** With `osd_name = None`, record the current/default input label — proves the delta and the zero-delta default.
- **Kernel-side, independent of the TV's UI.** Capture the bus (`cec-ctl --monitor` on a second handle) and confirm a `<Set OSD Name>` frame actually goes out in reply to the TV's `<Give OSD Name>` — a no-show here says the *kernel auto-reply* assumption failed (fall back to the proactive push), not that the TV ignored it. Also confirm **no premature `<Set OSD Name>`** is emitted at open on a clean adapter (the buffer-only claim).
- **TV-side relabel.** With a configured `osd_name`, confirm the HDMI input relabels (LG requires SIMPLINK enabled); note whether it takes on connect, on the next wake's `<Active Source>`, or only after a re-poll.
- **Persistence.** Confirm the label survives a TV power-cycle *without* a daemon reconnect (the wake-in-place payoff: the still-open tx fd keeps `cec_log_addrs` configured), and survives the TV's own remote-driven input switches.
- **No regression with SIMPLINK off.** Confirm turning SIMPLINK off simply falls back to the generic label rather than misbehaving.
- If the vendor-OUI follow-up is on the table, separately confirm it changes the icon on the C3/G4, and how the set behaves on GPU DisplayPort-CEC vs USB.

Record findings as the first entries in the protocol.md CEC Quirks table.

## Round 2 redesign: clear-means-default + an advertise toggle (post-QA + max review)

**Trigger.** Field QA on the shipped default exposed that the documented opt-out was unreachable: clearing "Input name" in the pairing wizard re-applied the `TisVlay` serde default (the shared form builder drops empty optional fields before they reach any payload), and clearing it in the TV edit pane changed nothing at all (the edit patch omits the key, and `apply_config_patch` only touches keys present in the patch — so the same gesture meant "default" on pair and "keep the old value" on edit). A 27-agent max review (10 verified findings) traced the tangle to one shape — `osd_name: Option<String>` with a `Some("TisVlay")` default and an empty-string-as-off sentinel — plus one genuine bug: the advertise call was fail-closed (`?`), so a cosmetic `set_osd_name` failure could deny all CEC power/screen control.

**The invariant.** Clearing an optional form field means **reset to the schema default** — uniformly, on both form paths, for every vendor. A state that is neither "default" nor "a valid value" (here: "advertise nothing") must be a first-class field, never a magic empty. No empty-string sentinels exist in vendor config; an explicit `""` is tolerated as a synonym for "absent" (the `de_physical_address` precedent), never as a distinct state.

- **Shared form layer (all vendors).** `build_config_json_from_schema` gains a cleared-optionals mode: the pair payload omits cleared fields (absent → serde default; the pairing params become TOML, which cannot carry null anyway), while the edit patch emits an explicit `null` — which the daemon's merge already interprets as "remove the stored key", letting the serde default reapply on the next parse. Zero server change: the patch vocabulary existed, only the form never spoke it. This also fixes a latent all-vendor bug: clearing a stored (wrong) LG MAC in the edit pane silently kept it.
- **CEC config shape.** `advertise_osd_name: bool` (default `true`) is the off switch — a Bool row always transmits, so it survives both form paths and the merge, mirroring `emulate_screen_via_power`. `osd_name` becomes a plain `String` (default from a single `DEFAULT_OSD_NAME` const shared with the schema default), killing the dead `Option` / `skip_serializing_if` plumbing, the unreachable `None` state, and the duplicated `"TisVlay"` literal.
- **Normalize at the config boundary.** `osd_name` deserializes through sanitize + 14-byte char-boundary clamp, empty → default — so the stored, displayed, and advertised names agree (the review's truncation-mismatch finding). Known residual: `update-config` merges raw vendor values without a schema parse, so a CLI-patched over-long name displays raw until the next pair-time round-trip; the connect path still advertises the clamped form.
- **Fail-open advertise.** A `set_osd_name` failure logs at warn and continues — a label must never cost power/screen control. The link-layer clamp stays as idempotent defense and as the single clamp implementation.
- **Test seam.** The fake opener records the clamped value production would advertise (not the raw config value), so clamp regressions become visible to the advertise assertions; the config round-trip test asserts `osd_name` explicitly; a GUI test pins the null-on-clear edit payload.
- **Supersedes:** the "empty string opts out" mechanism everywhere it was documented (config field docs, schema helper text, protocol.md), the `None`-default zero-delta story (already historical), and the review's suggestion to delete `de_physical_address`'s empty arm — unified tolerance (`""` ≡ absent ≡ default) beats a loud parse error for hand-edited configs, and `osd_name` now follows the same rule, which dissolves the per-row divergence by making the rows agree rather than by outlawing the input.

## Round 3: the fleet snapshot reads state, not rpcs (primary + INFO rows become published payloads)

**Trigger.** The round-2 regression fix (`5ce2c6e`) served the primary descriptor on the get-config *rpc reply* and kept a first-row fallback — both compat-shaped, and the investigation exposed deeper vestiges: `TvInfo.vendor_info` was write-never (a served-D-Bus-era remnant of `display_diagnostics`, never wired into the zenoh stack), the GUI's INFO rows came from `flatten_config` (raw alphabetized config *keys*, not the schema-ordered labels `display_config` was designed to provide), and `list_tvs` did a per-TV `get-config` rpc on every snapshot refresh solely to feed those rows (the code apologized: "small fleets").

**The shape.** Connector-derived display projections are *state*, so they ride the mirror like everything else clients render:

- `payload::Identity` gains `primary: Option<String>` — the connector's `primary_descriptor`, living beside name/vendor/brand/connector where it belongs. The get-config reply's `"primary"` key (added hours earlier) is reverted: one wire home.
- A new `payload::VendorRows { config, diagnostics }` publishes on `meta/vendor`: the connector's `display_config` / `display_diagnostics` rows — schema-ordered, labeled, default-backfilled, Secret-free. **Arrays preserve order on the wire; JSON objects do not** — which is the entire disease this cures. `vendor_info` comes alive for the first time in the zenoh stack (LG's WebSocket-scheme diagnostic row).
- The reactor computes all three at its existing `TransportFacts` sites (dial spawn + `Effect::Facts` on config change) — the established "config-derived facts the reactor evaluates because it owns the connectors" channel — and `spawn_tv` now also emits `Facts` at enrollment, so a deferred-dial (routeless) or never-dialed TV still publishes rows and primary.
- The SDK's `list_tvs` becomes a pure mirror projection: the per-TV get-config loop and `flatten_config` are deleted; `TvInfo.primary_descriptor` / `vendor_config` / `vendor_info` fill from the mirror row. The GUI drops the meaningless first-row fallback (an empty primary renders as "—") and its INFO rows switch from raw keys to proper labels for free.

The get-config rpc remains for what it actually serves: the edit-form prefill (raw values by key) and CLI inspection. `TV_PATHS` grows to sweep `meta/vendor` on removal.

## Non-goals / Open decisions

- **Default source of the name.** Ship `osd_name` defaulting to `None` (opt-in, zero-delta) for v1. Auto-deriving from the system hostname (Chromecast-style zero-config) is attractive but pulls a hostname read + its own ASCII/length messiness into the daemon path; propose it instead as a later GUI-side *prefill* — the pairing wizard suggests the hostname, the user accepts/edits — rather than a daemon default. Flagged for decision.
- **Whether the vendor-OUI lever ships at all.** Deferred here (see the follow-up section); the open question is whether a field test greenlights an off-by-default expert knob or whether it stays an idea. Decision belongs to the field result.
- **No dynamic rename.** The name is fixed at `open`; a config edit takes effect on the next reconnect, matching how `physical_address` / `emulate_screen_via_power` already behave. No live `<Set OSD Name>` push on config-patch.
- **No new capability, client gating, or power/screen/input behavior change.**
