# A wake reports success only once the TV has acted on it

## Goal

A power-on that the TV doesn't act on should keep trying for a short while, then fail visibly, instead of reporting success with the TV dark. Today two backend paths call a wake done before the TV has acted on it, and the world reports whatever they say:

- **LG's `wake_and_connect`** returns as soon as SSAP registers. An LG in `ActiveStandby` (for a few seconds after a remote-off) still accepts SSAP, so the dial connects on its first attempt, sends one WoL, and returns. On the #228 hardware checks, a power-on 1 s after a remote-off connected on attempt 1 and the TV stayed in `activestandby` until the remote turned it on; `progress/power` said `connected`.
- **CEC's in-place `power_on`** (a power-on over the live link of a TV in standby, the path most CEC power-ons take, because a CEC TV stays connected in standby and CEC emulates screen actions through power) sends one Image View On and returns. A frame the TV ignores leaves it off, and nothing reports it.

This retires [concerns/power-on-unverified.md](../concerns/power-on-unverified.md).

## Background

- **The contract.** [docs/backends/implementing-a-vendor.md](../backends/implementing-a-vendor.md): "`wake_and_connect()` owns *all* retry/backoff/probe logic for the wake path — the daemon calls it and treats it as atomic." Link and power are separate axes (`state/link`, `state/power`); `progress/power` is the wake flow's progress.
- **History.** `645f94de` (the dispatch QoS tiers) left power-on out of the verify tier on purpose, since "`power_on` already has WoL + retry inside": its reliability was delegated to each backend's wake. `378439a8` gave CEC's dial-path wake a re-send-and-poll loop after a field failure; the in-place `power_on` never got one.
- **The world's routing is already right** after #228: in place for a standby-reachable bus, a wake dial for a network TV that needs waking, satisfied for an awake one. What's missing is anyone checking that the wake landed.
- **What the reviews found** (design, implementation correctness, maintainability), folded in below: failing LG's dial on a refused wake would make the world treat a working link as a failed connect (publishing `connect-failed`, re-running the wake dial up to `CONNECT_MAX_ATTEMPTS`, then dropping the link); LG's power query can take ~25 s through `with_retry`'s hidden reconnect, so an attempt count doesn't bound wall time; CEC's `reachable()` accepts `ToOn`, which `is_awake` rejects; a TV that answers power queries with `Unknown` would fail every wake; re-claiming CEC's logical address in place would drop RC passthrough; and the trait docs, not the guide, are the contract's canonical home.

## Decisions

1. **Backends do the transport-specific trying; the world judges the outcome once.** A backend's wake (dial or in place) resends and polls within a short wall-clock confirm window, then returns what it has: the connection for a dial, `Ok` in place. It errors only for link problems, never because the TV refused. The world then judges the wake from the power state it leaves. Reason: the retry primitives (WoL, Image View On, re-claim) are transport-specific and stay in the backends, as the guide says; one vendor-agnostic verdict in the world covers every backend, the mock (the guide's template) and any future one, without a second retry layer, and keeps a working link up. Rejected: a world verify tier that retries (a second layer over the backends' loops); failing the dial on a refused wake (above).
2. **A wake failed only if the TV positively reports an off state:** `PowerState::class() == PowerClass::Off` (`Standby`, `ActiveStandby`, `Suspend`). `On`-class states (`Active`, `ScreenSaver`, `ScreenOff`) and `Transient` ones (`WarmingUp`, `CoolingDown`, `Unknown`) don't fail it: a warming-up TV has acted on the wake, and a TV that can't report its power state gets no false failure. The backends' loops poll until an `On`-class report or their deadline. No new core API.
3. **On `progress/power`, a wake dial ends `connected` unless its connection's power snapshot is `Off`-class, and then it ends `failed` with the link kept up.** No key, payload, phase or decode rule changes, so these are `fix` commits; the `PowerPhase` rustdoc says what each terminal phase now means.
4. **An in-place power-on publishes only `failed`, and the world judges it.** The connection task sends a plain internal `BackendEvent::PowerOnDone` after its post-command state refresh, and `facts.rs` judges from the cached power state with the same `Off`-class helper as the dial verdict, so the world judges in one place (decision 1). On `Off`-class it publishes `failed` with the dial-failure arm's cleanup: dropping a riding screen-on intent, which would otherwise escalate into a second in-place wake, and the pending input restore. A success publishes nothing, so the tray's wake toasts don't fire on every CEC screen-on. No new wire value.
5. **An off-going command interrupts an in-place wake.** While an in-place `PowerOn` runs, the connection task also takes commands; a `PowerOff` or `ScreenOff` abandons the wake and runs (latest intent wins, as a later off already cancels a held wake). The abandoned wake skips the verdict and reports `failed`, as a cancelled held wake does, so a client following it stops waiting. Other commands wait, in order. Reason: a power-on, then a power-off, then the sleep's drain, run one after another, would outlast logind's default 5 s inhibit delay, and the PC would sleep with the TV on.
6. **The one wake failure left that errors is LG's deadline, and it uses `Error::Backend`.** A refused wake no longer errors anywhere (decision 1). A new `tisvlay_core::Error` variant would be published API for a case the world doesn't need to tell apart.
7. **The contract lives in the trait docs** (`TvConnector::wake_and_connect`, `TvConnection::power_on` in `tisvlay-core`'s `traits.rs`), stated once; the vendor guide gives a clause and a link, and `architecture.md` describes only the world's verdict.
8. **No new tuning places.** LG's wake budget becomes one wall-clock deadline (replacing `WAKE_CONNECT_MAX_ATTEMPTS` as the bound) plus a short confirm window; CEC's `WAKE_VERIFY_*` constants are renamed `WAKE_CONFIRM_*` so they don't read as the world's verify tier (`RetryConfig`, `DispatchVerify`), which stays screen-only.
9. **The windows.**
   - **LG:** the dial runs to a 30 s deadline that starts once the first WoL send succeeds, so the NIC-recovery backoff after a PC resume (`wake_with_retry`) doesn't eat into it. After each connect, an 8 s confirm window polls the power state every 0.5 s and resends WoL every 1 s, which outlasts the remote-off latch (about 1 s, with turn-on accepted after ~5 s per `lg/firmware-quirks.md`) without flooding a broadcast reflector.
   - **CEC:** the dial keeps today's 6 s, so a slow TV isn't newly reported failed. In place runs 4 s, since it holds other commands to that TV: it polls from ~300 ms, backing off, and resends Image View On every 1.5 s. The two windows are separate named constants.
   - Step 5 confirms or adjusts them, recorded as a deviation if it does.
10. **Loops are tested under paused time with seams,** not against sockets: each backend's loop is factored over closures (connect, read power, send wake), so LG's needs no fake SSAP server and no real WoL broadcast; `tisvlay-lg` gains `tokio`'s `test-util` dev-feature. CEC's fakes gain `FakeCecLink::with_ignored_wakes(n)`, and the mock gains `set_power_on_ignored` (named after `set_power_on_closes`) and `power_on_delay_ms` (beside `power_off_delay_ms`).

## Steps

Each step carries its own doc and comment updates, so the tree's docs match its code after every commit.

1. **World: judge a wake dial by its connection's power snapshot.** In the `Connected` arm for a wake dial (`facts.rs`), publish `connected` unless `state.power_state` is `Off`-class, else `failed`, through one `wake_failed` helper that step 4 reuses; the link stays. A `failed` verdict drops the pending input restore (`DesiredInput`), which would otherwise send `switch-input` to an off TV until its budget ends in `dispatch-failed`. It doesn't drop a riding screen-on intent: the verify's `escalated` flag already bounds it. Docs: `PowerPhase` rustdoc (`tisvlay-protocol`; including that a `Transient` reading such as `CoolingDown` ends `connected`), `BackendEvent::PowerPhase` docs, `architecture.md`'s key table and power-path paragraph. Tests (world, on the mock): a wake dial that connects into `ActiveStandby` (`set_initial_power_state_override`) publishes `failed`, keeps `state/link` connected, and publishes no `connect-failed`; into `Active`, `connected`; into `WarmingUp` or `Unknown`, `connected`; a `failed` verdict sheds an armed input restore. `escalation_reasserts_on_reconnect_then_gives_up`, which wakes into `ActiveStandby`, keeps passing unchanged (its re-assert, retries and `dispatch-failed` don't depend on the phase).
2. **LG: the wake resends WoL until the TV is on, within a deadline.** Factor `wake_and_connect`'s loop over closures, with a `pub(crate)` seam on `LgConnection` to reach its raw client: the polls go to the client, not `LgConnection::get_power_state`, whose `with_retry` reconnects underneath. The dial runs to its deadline (decision 9). After each connect, the confirm window polls the power state, each poll bounded with `timeout_at` to the next tick or the window's end (a raw request otherwise waits `REQUEST_MS`, longer than the window; dropping it is safe, since the transport discards a late reply), and resends WoL (`wol::wake_best_effort`) every 1 s. A timed-out or `Unknown` poll is "not on yet". A closed or broken link (`ConnectionClosed`, `Connection`, `Io`: the set `with_retry` treats as stale) drops the connection and re-enters the connect phase within the deadline, with the confirm window restarting at the next connect, so only a live connection is ever returned. Return at an `On`-class report or when the window ends; a dial that never connects by the deadline fails with `Error::Backend`. `tisvlay-lg` gains `tokio`'s `test-util` dev-feature. Tests under paused time: already `Active` returns at once with no extra wake; `ActiveStandby` for N polls then `Active` returns after N+1 polls with wakes sent between; never on returns the connection at the window's end; timed-out polls don't end the loop; a link that closes mid-window reconnects and returns a live connection; a TV that never accepts a connection fails at the deadline. Docs: the LG connector's constant and comment docs (including "the only retry layer"), `TvConnector::wake_and_connect`'s rustdoc (the contract), the guide's clause, and `lg/firmware-quirks.md`'s remote-off latch section.
3. **CEC: the in-place power-on resends and polls.** Put the send/sleep/poll skeleton beside the `CecLink` seam (`link.rs`, or a new `confirm.rs`; not `wake.rs`, which would sit beside `wakeup.rs`, the wake-the-PC module), used by the connector's `wake_and_connect` and by `CecConnection::power_on`, with a closure for a send error: the dial path re-claims as now, while in place resends on the held link only (no re-claim, so RC passthrough survives). Poll early and back off, resending every 1.5 s, for the path's window (decision 9); `Err(ConnectionClosed)` still returns at once (it drives `PowerOnLost`). Both paths return at an `On`-class report or the window's end: `power_on` with `Ok`, and the dial with its connection instead of today's `Error::backend("TV did not report power-on …")`, leaving the verdict to the world. `reachable()` gives way to `class()`. Tests on `FakeCecLink` under paused time: `with_ignored_wakes(2)` wakes in place on the third send; `with_ignored_wakes(usize::MAX)` returns after the window with the TV in standby, in place and on the dial path (which now returns its connection); `power_on_wakes_in_place_on_the_existing_link` moves to paused time; the dial-path tests and the daemon's `cec_power_cycle_keeps_the_link_up` keep passing. Docs: `TvConnection::power_on`'s rustdoc (replacing its stale fallback sentence), the CEC connector and connection module docs, `docs/cec/protocol.md` (its in-place description and fallback), `docs/cec/testing.md`, and `docs/ideas/power-vocabulary.md` (it names `WAKE_VERIFY_*`).
4. **World: an in-place power-on is judged, and an off interrupts it.** After an in-place `PowerOn` and its existing state refresh, the task sends `BackendEvent::PowerOnDone`; `facts.rs` judges from the cached power state with step 1's helper and, on `Off`-class, publishes `failed` with the dial-failure arm's cleanup (the screen-on intent and the input restore). While the `PowerOn` runs, the task runs an inner `select!` over the pinned wake future (the only borrow of the connection), `cmd_rx`, the state subscription and the event channel. A `PowerOff` or `ScreenOff` drops the wake (cancel-safe: each CEC link operation awaits a oneshot from linux-cec's worker, which discards an abandoned result), skips the verdict, reports `failed`, and runs next; other commands queue locally behind it and run in order, `Drain` included, so a sleep's inhibitor handoff still follows its `PowerOff`. The GUI's first-phase grace rises to 6 s for every TV: the wire doesn't say which TVs are standby-reachable, and nothing renders or blocks during the grace. Its follow loop is factored over a phase stream and the ack future, for a paused-time unit test. The SDK's `power_on` rustdoc says an in-place power-on reports only a failure. Tests: world (an ignored in-place power-on publishes `failed`, keeps the link, and drops the screen-on intent and the input restore; a `PowerOff` sent during a delayed in-place wake runs at once and the wake reports `failed`), GUI unit (a late `failed` reaches the row). Docs: the book's troubleshooting phases, `lg/benchmarks/wake-reconnect.md`'s CEC power-cycle note.
5. **Hardware check** (unattended, logging to a file, CEC Image View On as the safety net, as in #228's probe). Before each iteration, restore the precondition (TV awake, LG link up, both getters reading on), and log the cached power state when the power-on is sent. Record `tisvlay watch` with timestamps for `progress/power` and `event/connect-failed`.
   - LG: a CEC `<Standby>`, then an LG `power on` after 0.5, 1, 2 and 4 s, twice each: each ends with the TV on and `connected`, or `failed` with the link still up. A send at 0.2 s may find the cache still `Active` (LG reports the transition ~200 ms later), which the world treats as already on; log it as its own outcome rather than a failure of this change.
   - CEC in place: `power on` to the CEC TV from standby, several times; the TV wakes each time.
   - CEC dial path, if the adapter can be dropped and brought back: the TV disconnected, then `power on`, since step 3 changes how that path ends.
   - Optional, with the maintainer at the remote: a real remote-off, then `power on`.
6. **Retire.** Delete the concern and its index entry, move the plan's lasting decisions into their homes (the trait docs, `architecture.md`), delete this plan and its Active plans entry, and sweep inbound references. The open questions below move to `docs/ideas/` as deferred work, the dialing-wake race among them.

## Open questions

- **A power-off during a dialing LG wake isn't cancelled** (`cancel_held_wake` leaves a wake that's already dialing), so the confirm loop can resend WoL briefly after an off. The confirm window bounds it, though its 8 s widens it slightly; a mid-loop awake-to-off edge could also stop it.
- **A screen intent's in-place wake** never reaches `dispatch-failed` (`verify_dispatch` sends `PowerOn` and drops the latch). No current backend is standby-reachable without emulating screen through power, so this is noted, not fixed.

## Deviations

- **Step 4: an in-place wake's input restore isn't held for the wake.** For a TV woken in place the link is already up, so `reconcile_input` sends its switch at once, and the connection task runs it after the wake (commands run in order). After a failed in-place wake, that one switch still reaches the off TV; the `PowerOnDone` verdict drops `DesiredInput`, so nothing retries. No backend wakes in place with `INPUT` today (CEC sheds the restore by capability), so holding the restore until an in-place wake lands, which needs a marker the reconcile can wait on, is noted for the retirement step's `docs/ideas/` entry rather than built. The step's world test covers `failed` and the kept link, not the input.
- **Step 5 found a false `failed`, fixed in its own commit: the in-place verdict judges the state the refresh read, not the world's cache.** In one of four in-place CEC trials, the post-command refresh's power query timed out while the TV was busy announcing itself after waking, so no state was sent and the verdict judged the cached pre-wake standby. `PowerOnDone` now carries the power state the refresh read, or none when it failed, and none doesn't fail a wake (decision 2: a TV that can't say gets no false failure).
