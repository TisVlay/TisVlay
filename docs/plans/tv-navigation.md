# TV remote and gamepad navigation

## Goal

Make the settings GUI usable from the couch: a TV remote or a gamepad, on a TV across the room. Plasma Bigscreen is the target session, and the one QA surfaced the gap on. Today the remote can reach almost nothing. Most of the GUI's actions are pointer-only click areas, focus is invisible where it does land, and the window is sized for a desk.

The result should also be a better keyboard-only GUI on any desktop, since the remote arrives as keys.

## What the remote delivers

Researched on a KDE neon VM (Plasma Bigscreen 6.8.2, a DualShock 4 over USB), in the upstream source, and with Slint 1.18.1 experiments on the testing backend.

- **Bigscreen turns controllers into keys.** `plasma-bigscreen-inputhandler` reads gamepads through SDL3 and CEC remotes through libcec, and replays them as evdev key presses through the xdg RemoteDesktop portal. The GUI sees an ordinary Wayland keyboard, so TisVlay needs no gamepad or CEC input code.
- **Slint keeps only the keys it can name.** Its winit backend drops a key that has neither a Slint name nor text. Two keys Bigscreen sends fall in that gap: the gamepad's Square sends KEY_MENU, which xkb maps to `XF86MenuKB` (the keyboard Menu key is KEY_COMPOSE), and Share and L2 send KEY_BACK, `XF86Back`, which winit names `BrowserBack` but Slint has no name for. Forward, Games, Cancel and Home are dropped too. What arrives:

| Key | Gamepad | CEC remote |
|---|---|---|
| Arrows | D-pad, left stick | Arrows |
| Return | Cross (A) | Select |
| Escape | Circle (B) | Back/Return, Exit |
| Tab, Shift+Tab | R1, L1 | — |
| dropped: `XF86MenuKB` | Square (X) | — |
| dropped: `XF86Back` | Share, L2 | — |

- **Escape is Back.** The gamepad's Circle sends Cancel and Escape together, and the CEC Back key sends Escape, so one key means Back on both.
- **L1 arrives as Shift+Tab, never as Backtab.** Slint turns Shift+Tab into backtab itself; a handler that wants "previous" checks both.
- **The on-screen keyboard follows text focus, from the remote's own input path.** Bigscreen sets `KWIN_IM_SHOW_ALWAYS=1`, and its keyboard pops up as soon as keyboard focus reaches a Slint text field from the gamepad, and types into it. A hardware keyboard, or a virtual one injected on the VM, doesn't raise it: KWin shows the virtual keyboard by the last input device. So what the D-pad and Circle do with the keyboard up is checked at the controller, not by injection.
- **No stream false positive.** The input handler's portal session doesn't register with the session's stream detector: `stream/state` stays empty while the controller drives the UI.

## What the GUI lacks

From an audit of the UI at the branch point:

- **Unreachable actions.** About 12 shared widgets (IconBtn, DangerBtn, UriBtn, CopyBtn, LinkText, interactive Chip, InlineError's buttons, SpinStepper) and about 8 one-off elements (sidebar items, Reload, TV and profile list rows, both "+" buttons, DiscoveryRow, the About brand area) are `TouchArea`-only. A remote can't reach navigation, TV or profile selection, Pair, Edit/Save/Cancel, Rename/Delete/Duplicate/Reset, the per-field restore-input and stream-gate toggles, Copy, Remove TV, or any About action. Settings is the only fully reachable pane.
- **Invisible stops.** The window-filling `nav-scope` FocusScope (`main.slint`) is a Tab stop and the initial focus. Every contextual-help "i" is a stop with no ring that Return doesn't open.
- **No shared focus ring.** Std widgets draw fluent's thin focus border, and a focused Slider shows only its pressed look. ThemedSelect uses an accent border that also means "open"; ThemedSpinBox draws its own accent border.
- **Dialogs aren't modal to the keyboard.** ConfirmDialog and NameInputDialog don't take focus or handle Escape, and Tab walks into the page behind. The pairing wizard, TV config edit mode and profile rename don't focus their first field, and `LineEditField` has no `forward-focus` for a caller to focus it through.
- **No Back.** Escape works in three places: an open select, a pinned help bubble, the rename field.
- **Focus is easily lost.** When the focused item is hidden or destroyed, Slint clears focus, and with no focus it runs no key handler at all, only the built-in Tab. This UI destroys focused items often: `if`-gated panes, the Edit/Save/Cancel and Rename buttons that swap, a dialog closing, and model refreshes that replace a whole nested `ModelRc` (the About components, a TV's vendor config and info rows, a profile's "used by" links) on every state reconcile, even with equal content.
- **Hover-only content.** Every icon-button tip, the About component health tips, the DiscoveryRow permissions remedy and the Reload tip.
- **Fixed desk sizing.** A 720×480 minimum and preferred size, compile-time `Design` tokens, about 267 literal px values, no scale handling, and a Settings pane with no ScrollView. The TV list is a virtualized `ListView`, whose rows outside the viewport don't exist for focus.

Slint gives us more than expected in two places: Tab/Backtab traversal is built in (item-tree order, skipping hidden items), and a newly focused item is scrolled into view through every enclosing scroll area. It has no arrow-key navigation, and no public "focus next" API in `.slint` or Rust.

## Decisions

1. **The GUI binds no gamepad or CEC input; it reads keys.** The vocabulary is arrows, Return, Escape, Tab/Shift+Tab and Menu. The winit event hook remaps the two keys Bigscreen sends that Slint drops: `XF86MenuKB` to Menu and `XF86Back` to Escape, through a pure mapping function. (Checked on the VM with a virtual keyboard: KEY_MENU arrives as `XF86MenuKB`, KEY_BACK reaches the focused GUI and changes nothing, and no KDE global shortcut binds either; Bigscreen's own apps treat Qt's Back like Escape through an in-app filter.) **Invariant: every function is reachable with arrows, Return and Escape alone**; Tab and Menu are accelerators, since CEC remotes have neither. Space, Alt+arrows and the mouse's back and forward buttons keep working. *Why:* Bigscreen already owns the device side, and a key-level contract works under any session that maps a remote to keys, and with a keyboard.
2. **One focusable base, and one ring on every focusable.** A Rectangle-rooted component with an inner FocusScope (behind its click area, so the first click isn't spent on focus) owns `accessible-role`, `accessible-enabled`, `accessible-action-default` and Return/Space activation, all calling one `activated` callback; widgets moved onto it drop their own `accessible-action-default`. The std Button, Switch and CheckBox are replaced by themed widgets on the base, as ThemedSelect already is, so a std control doesn't draw fluent's stroke inside our ring; Slider and LineEdit keep fluent inside a wrapper that draws the ring keyed on their `has-focus`. One focus look, and the ring stays on a focused control that turns disabled. The ring is an accent outline, 2px, 3px outside the control with its corner radius (chosen from a rendered matrix of the candidates): `Theme.focus-ring` for the color, `Design` tokens for width and offset. The ring shows only after keyboard input (a focus-visible flag set by a navigation key and cleared by a pointer press), and a click focuses the control it hits, so mixing the pointer and the D-pad resumes where the pointer was. *Why:* one activation callback per widget instead of two, and a ring that reads at distance, without rings appearing after every mouse click on a desktop. The accessible actions matter here as a test surface: the `accessibility` feature is off in production.
3. **Up/Down step through the Tab order; Left/Right adjust values or jump columns.**
   - Up/Down always move to the previous/next stop. `nav-scope` takes them in its `capture-key-pressed`, so they're taken from text fields too, except while a ThemedSelect is open (it owns them then).
   - Left/Right go to the focused control first: a slider or a spin box steps its value, a text field that's editing moves its cursor. Otherwise `nav-scope`'s bubbling `key-pressed` jumps columns with explicit `focus()` targets, no geometry: Left from a detail goes to its selected list row, Left from a list or a single-column pane goes to the active sidebar item, Right goes back to the pane's remembered stop, or its first.
   - Up/Down movement synthesizes Tab/Backtab synchronously from a Rust callback, marked so `nav-scope`'s own Tab handling (decision 10) never consumes it. *Why:* the Tab order already matches each column's reading order, so linear stepping inside a column plus cheap column jumps covers the GUI without row/column geometry. Synthesized Tab is the only "next" Slint offers. The winit hook can't do this part: it runs before Slint, so it can't tell a key a slider used from one nobody used. True 2D navigation goes to an idea doc.
4. **Every transition names where focus lands, and lost focus recovers.**

| Transition | Focus lands on |
|---|---|
| Dialog closes | Its opener; the selected list row or active sidebar item if the opener is gone (Remove TV) |
| Edit saved or cancelled | The Edit button |
| Field reset | That row's control |
| Wizard exits | The new TV's row, or the TVs "+" |
| Return on a sidebar item | Stays on the item |
| Return on a list row | The detail's first stop (decision 8) |
| History back | The stop that triggered the forward move (an anchor kept per history entry), else the active sidebar item |

   The models refreshed on every reconcile are diffed in place, as the TV and profile lists already are, so a state burst doesn't destroy the focused Copy, Config or "used by" button. A key that arrives while nothing has focus places focus on the last anchor instead of being lost. Detection: Slint sets a FocusScope's `has-focus` only on the focused scope, never on an ancestor, so `nav-scope`'s capture handler counts the keys it sees, and the Rust key router (the winit hook in production, the test helper in tests) compares the count around each dispatch; a key that didn't move the count arrived without focus. *Why:* focus lost on a remote leaves every key handler dead, and Bigscreen's own apps place focus explicitly on every page change and dialog.
5. **Escape: the innermost surface handles it, `nav-scope` handles the rest.** An open select, a dialog, an edit mode and a text field that's editing each handle Escape themselves. `nav-scope`'s fallback runs in this order:
   1. Close any visible help bubble, however it opened.
   2. The pairing wizard mirrors its footer: Back if enabled, else Cancel if enabled, else nothing (during the pair step).
   3. A detail goes to its selected list row.
   4. A list goes to the active sidebar item.
   5. On the sidebar: history back if the current page was reached through a click-through (a profile pencil, a "used by" link), else close the window in couch mode and do nothing on a desktop.

   A TV config edit with changes asks before discarding them; one without changes cancels at once. Rust exposes the state `nav-scope` needs: whether a modal is open, and whether history can go back. *Why:* going up the hierarchy before back in history is how Bigscreen's apps, Android TV and Kodi behave, and Back at the top exits on Bigscreen. One press of Circle shouldn't throw away a config typed on an on-screen keyboard.
6. **Help: ringed "i" stops, with Menu as a shortcut.** Each "i" becomes a focusable-base stop that opens its help on Return, so help is reachable on any remote. Menu toggles the focused row's help, or its section's, without moving focus; `nav-scope` takes it in its capture phase, before a LineEdit's built-in context menu sees it. Help opened by Menu closes when focus leaves the row. An icon-only button shows its tip after focus lingers on it. *Why:* CEC remotes have no Menu key, so the "i" stays, and Menu saves presses on a gamepad. The icon tips are the only explanation of a glyph.
7. **Dialogs hold focus.** ConfirmDialog focuses Cancel, the safe choice, by rule; NameInputDialog focuses its field. Both cancel on Escape, cycle Tab and Shift+Tab/Backtab among their own enabled controls with explicit `focus()` calls, and focus lands per decision 4 on close. They're `visible: open`, so `changed open` can focus without deferral. Fields created inside an `if` (rename, config edit) focus in their `init`; if the compiled app trips Slint's property-recursion guard there, a zero-interval `Timer` defers it. The guard was observed on Slint 1.16.1 and didn't reproduce on 1.18.1 in the testing backend. *Why:* the two dialog components cover all six dialog call sites, and Slint's traversal can't be scoped to a subtree.
8. **List rows select on Return and move focus into the detail.** TV, profile and discovered-TV rows become focusable stops; Return selects the row and focuses the detail's first stop (for a discovered TV, the footer's Next, past the manual-entry fields). Escape comes back to the row. The TV list becomes a ScrollView over a `for`, so every row exists for focus. *Why:* stepping through a list doesn't swap the detail on every press, and Return-to-open is how Bigscreen's lists behave.
9. **Couch mode, detected or chosen.** A per-user GUI preference in the Settings pane, Auto / On / Off plus a scale factor, saved to the GUI's own small file in the user's config directory, the GUI's first preference of its own. `TISVLAY_COUCH_MODE=auto|on|off` overrides it for testing. Auto turns couch mode on from a list of 10-foot-session signals, starting with Bigscreen's `PLASMA_PLATFORM=mediacenter`. *Why:* the GUI starts through D-Bus activation with no arguments, and a second launch hands off to the running window, so a launch flag can't reach it. A plain desktop session driving a TV gets no signal and needs a way in, and the right scale depends on the screen and the distance.
10. **What couch mode changes.**
    - The window opens maximized (`Window::set_maximized`).
    - The UI scales by the preference's factor (default 1.4, Bigscreen's 18px body font over our 13px) on top of the compositor's scale: the winit hook multiplies each compositor scale event, and the GUI applies it once after the window opens. `SLINT_SCALE_FACTOR` isn't used: it replaces the compositor's scale, and setting it in-process would mean `set_var` after the runtime's threads start.
    - The 720×480 minimum is relaxed, since a scaled maximized window can be smaller in logical pixels.
    - Focus starts on the active sidebar item at launch and on re-activation.
    - Tab and Shift+Tab cycle the panes TVs → Profiles → Settings → About, as console menus do with their shoulder buttons. A desktop keeps standard Tab.
    - Text fields stop at a ring first and start editing on Return (bringing up the on-screen keyboard); Return or Escape stops editing and keeps focus on the field. A desktop edits on focus, as now.
    - Copy buttons leave the focus order: a clipboard is little use on a couch session.
    - Escape on the sidebar closes the window (decision 5).

    *Why:* a uniform relative scale covers the literal px values a token-only large mode would miss, and still honors the session's own display scale. The rest follows 10-foot conventions without changing desktop behavior. A layout with its own couch tokens isn't planned.

## Steps

Each step is a commit on `feat/bigscreen`, and a step that settles a spike writes the result into its decision, and into Deviations if it departs from the plan, in the same commit. GUI tests drive keys through `slint::Window::dispatch_event` on the testing backend. Focus is observed through the ring: its opacity is bound to `has-focus`, and tests read it with `ElementHandle::computed_opacity()`. Hardware checks run on the neon VM with the DualShock 4 under Bigscreen, and from step 5 on they use arrows, Return and Escape only, the CEC subset.

1. **Key-test harness, and `nav-scope` out of the Tab order.** A shared test support module (moving `find_by_accessible_id` and `count_by_id` out of the About tests) gains a key helper that sends press and release, sends L1 as Shift down, Tab, Shift up, and advances mock time and pumps timers after each key. Its first use: `nav-scope` stops being a Tab stop, keeping `focus-on-click` so a background click still dismisses help. `docs/testing.md` gains a "Driving keys" paragraph, and the contextual-help test's comment that focus is untestable is corrected. Spike on the VM, recorded in decisions 1 and 4 and under What the remote delivers. *Verified by:* a test that one Tab from a fresh Settings pane lands on its first switch (Return fires `Tray.set-notification`), and that Shift+Tab from there wraps to the pane's last stop rather than the window scope. The Tab count is the number of stops before the pane: step 3 raises it when the sidebar becomes focusable.
2. **The focusable base and the ring.** The component, the `Theme.focus-ring` and `Design` ring tokens, the focus-visible flag, and the wrapper for std widgets. The shared widgets move onto it: IconBtn, DangerBtn, UriBtn, CopyBtn, LinkText, interactive Chip, InlineError's buttons; ThemedSelect and ThemedSpinBox adopt the ring, distinct from ThemedSelect's open look. ThemedSpinBox steps on Left/Right; SpinStepper stays pointer-only. The HelpTrigger comment that hover hosts carry no FocusScope is updated, and `docs/gui/theme-breeze.md` follows the new token. New accessible labels go through `just i18n-extract`. *Verified by:* tests that Tab to each widget kind, see its ring, and fire it with Return. On the VM, the ring reads at distance on every kind, slider included.
3. **The one-off controls and list rows.** Sidebar items, Reload, both "+" buttons, the About brand area, and TV, profile and discovered-TV rows, with Return-to-select and focus into the detail. The TV list becomes a ScrollView. Elements without one gain accessible labels and `accessible-id`s; `AboutSlint` stays pointer-only (it hands off to a browser). `just i18n-extract`. *Verified by:* tests that pick a TV and a profile, and start pairing, by keys alone. On the VM, every pane is walkable with R1/L1.
4. **Couch mode.** Detection as a pure function of the preference, the override and the session's signals; the preference file; the Settings pane control; maximize, the relative scale through the hook, the relaxed minimum, launch focus; and a ScrollView for the Settings pane, which clips first at a large scale. `just i18n-extract`. *Verified by:* unit tests of detection and of the preference file. On the VM, launching from the Bigscreen app grid (D-Bus activation, not a terminal) opens maximized and scaled, and a later desktop login doesn't inherit the signal. The default scale isn't judged on a real TV in this train: it comes from Bigscreen's own font ratio, and the preference lets it be tuned from use.
5. **Arrows.** Decision 3's rules, the column jumps' targets, couch mode's Tab pane cycle, and Copy buttons out of the couch-mode order. Slider writes from a held D-pad are checked for coalescing, and coalesced if they aren't. *Verified by:* tests for stepping, for an open select keeping Up/Down, for a slider and a spin box keeping Left/Right, for a text field losing Up/Down, for each column jump, and that a synthesized Tab is never taken for a pane cycle. On the VM, the D-pad walks every pane and reaches Remove TV from the sidebar.
6. **Focus survives.** Decision 4: the landing table, in-place diffing of the refreshed models, and recovery from lost focus. *Verified by:* tests that focus survives a state refresh on a Copy button, and lands per the table after each transition. On the VM, the D-pad never goes dead.
7. **Dialogs, edit modes and text fields.** Decision 7, the dirty-edit confirm, and couch mode's edit-on-Return text fields. The rename field's "user clicks into the field" comment goes. *Verified by:* tests that a dialog opens on Cancel or its field, cycles inside itself, skips a disabled confirm, cancels on Escape and returns focus to its opener, and that a rename focuses its field on entry. On the VM, a dialog's field takes text from the on-screen keyboard, and Circle with the keyboard up does what step 1 recorded.
8. **Escape walks back.** Decision 5's fallback chain in `nav-scope`, the modal and history state from Rust, and the hook's `XF86Back` remap. *Verified by:* a test per level of the chain, including two Escapes walking two history entries, and a unit test of the remap. On the VM, Circle and Share back out level by level, and close the window from the sidebar.
9. **Help.** Decision 6: ringed "i" stops, Menu in `nav-scope`'s capture phase, the hook's `XF86MenuKB` remap, help that closes when focus leaves the row, and focus-lingered icon tips. *Verified by:* tests that Return on an "i" and Menu on a row open help, that Menu on a LineEdit opens help rather than its context menu, and that leaving the row closes it. On the VM, Square opens and closes help.
10. **Docs, and retire the plan.**
    - The focus and key model in a new `docs/gui/remote-navigation.md`.
    - `docs/gui/contextual-help.md` updated for the "i" stops and Menu.
    - `docs/concerns/slint-gotchas.md` gains the dropped keys, the focus-loss rule and the zero-width std FocusScopes.
    - `docs/concerns/slint-unstable-winit-030.md` lists the new hook call sites.
    - A section in the book's `guide/gui-tray.md` on driving the GUI with a remote and couch mode, agnostic to the session (Bigscreen as an example), including remapping a CEC remote's Info key to Menu in the input handler's settings.
    - `docs/ideas/gui-spatial-navigation.md`, indexed under GUI: 2D navigation, the inline row editor for profile rows, focus-following selection, and a couch-mode hint strip.
    - The plan file is deleted, with its README entry.

    *Verified by:* `just docs-links`, and the sweep for inbound `docs/plans/tv-navigation` references.

Packaging, the `.desktop` file, the D-Bus service file and the NixOS module need no change: couch mode is detected and stored by the GUI itself.

## Deviations

- **Step 1: Tab can't reach a stop under a clipping element while it's scrolled out of view.** Slint's traversal forgives an item hidden only by a `Flickable`, but its walk stops at the first clipping ancestor, and that ancestor's own clip rect is already empty below the fold, so a `TextInput` or FocusScope under a `Rectangle { clip: true }` is skipped while a bare one is reached (checked on the testing backend with `i-slint-core` 1.18.1, `item_tree.rs` `is_visible_or_clipped_by_flickable`). `LineEdit` clips its `TextInput` (`lineedit-base.slint`), so every `LineEditField` below the fold of a detail was unreachable by Tab, which is what the VM showed in the TV config edit form; `ThemedSpinBox` has no clip and is reached. Fixed in its own commit: `LineEditField` gained a reach scope outside the clip that takes the Tab and forwards focus programmatically (programmatic focus ignores visibility and still scrolls into view), disabled from the field's own Shift+Tab so leaving backwards doesn't bounce; the schema form's password field goes through `LineEditField` too, and the field gained `forward-focus` for callers. The focusable base keeps its FocusScope outside any clip. Tests: Tab reaches the edit form's name field below the fold, and Shift+Tab leaves it.
- **Step 6: the dialog row of the landing table lands with step 7.** Where focus goes when a dialog closes is part of making the dialogs hold focus, so it ships with that step rather than before the dialogs take focus at all. A landing made without a key (the wizard closing, a history step) places focus but doesn't show the ring; the next navigation key does, as everywhere else.
- **Step 5: slider writes were already coalesced.** Volume and backlight go through the GUI's `Coalescer` before the daemon, so a held arrow key sends the last value, not a stream; nothing to add.
- **Step 4: the preference file is `gui.toml`, and it's the GUI's advertised config file.** The GUI's D-Bus interface already exposed a `config_path` property, empty until the GUI had settings, and the About pane's GUI row left its Config button disabled for the same reason; both now point at `gui.toml`, so the file is reachable the way the daemon's, session's and tray's are. The couch-mode scale is shown and stored as a percentage in the Settings pane (`ThemedSpinBox` is an integer control) and as a factor in the file.
- **Step 3: the profile detail's entry stop is Duplicate, not the header's Rename.** A `forward-focus` target can't sit inside a conditional, and the header's Rename and Delete buttons swap with the rename field, so Return on a profile row lands on the FIELDS toolbar's Duplicate button (the TV detail lands on its Power button as planned). The profile detail is also created by the very activation that requests focus, so it takes a pending request on `init`, through a served-request marker the pane keeps, rather than only on a tick change.
- **Step 1: the element query prunes what's scrolled out of view.** `ElementQuery` skips items whose clip rect doesn't contain them, so a test that asserts on a control below the fold sizes the window tall first (`window().set_size`); the key helper's docs say so.
