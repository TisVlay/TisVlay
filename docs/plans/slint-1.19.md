# Slint 1.19

## Goal

Move the GUI to Slint 1.19 as its release approaches, and use the bump to pay down what the release makes unnecessary: workarounds for upstream bugs 1.19 fixes, plumbing of our own that 1.19 offers an API for, and whatever the new compiler diagnostics point at. The UI opts into edition 1.19, the first edition, so the GUI follows the language where it's going rather than where it was.

The bump itself was mechanical: the three pins moved and the GUI compiled first try, with one new compiler warning, and the whole GUI test suite passed on the pre-release branch. The paydown is where the judgment is, and this plan is its record.

## What 1.19 changes for this GUI

From the [pre-release changelog](https://github.com/slint-ui/slint/blob/pre-release/1.19/CHANGELOG.md), the branch's source, and the upstream trackers the GUI's docs cite, checked on 2026-11-09 against `pre-release/1.19` at b4448d86.

**Fixed upstream.**

- Tab reaches a focusable under a clipping element while a scroll view hides it ([#13614](https://github.com/slint-ui/slint/pull/13614)). `LineEditField`'s reach scope exists in part for this.
- The interpreter's "accessing deleted parent" crash on a callback that destroys its own element ([#6426](https://github.com/slint-ui/slint/issues/6426), closed 2026-10-18). `docs/concerns/slint-live-preview-nav-crash.md` tracks it.

**Still open, so the workarounds stay.**

- Native winit popups ([#11740](https://github.com/slint-ui/slint/pull/11740)) are still an open pull request: `ThemedSelect` stays, and the ComboBox concern with it.
- The accesskit panic ([#10269](https://github.com/slint-ui/slint/issues/10269)) and the missing window-focus API ([#4382](https://github.com/slint-ui/slint/issues/4382)) are open: the accessibility idea and the `unstable-winit-030` concern stand.
- A read-only `TextInput` is a Tab stop ([#13761](https://github.com/slint-ui/slint/issues/13761)) and a `FocusScope` eats the press that focuses it ([#12044](https://github.com/slint-ui/slint/issues/12044)): the bare-input field and `focus-on-click: false` stay.
- The three findings from the remote-navigation train (`changed has-focus` skipped on creation, `ContextMenu` opening on the Menu key's release, a programmatic `focus()` walking into hidden items) reproduce on the branch, as checked with the standalone reproducers on 2026-11-07. Their workarounds stay; filing them is held for the maintainer's review and isn't part of this train.

**New, where the GUI has plumbing of its own.**

- `ensure-visible(behavior)` on every element scrolls the enclosing Flickables by the smallest amount that brings it into view, edge to edge and with no margin. `Nav.reveal` and `HelpScrollView.keep-in-view` exist for the margin, so they stay. `ThemedSelect`'s flyout scrolls to the keyboard cursor with arithmetic over the row height and the visible count; the cursor row can ask for itself instead.
- `Flickable.scroll-to()` and `ListView.ensure-row-visible()`: no caller here (the lists are a `ScrollView` over a `for`).
- `fontique_012::set_shared_collection()` (feature `unstable-fontique-012`) hands Slint a font collection before the platform initializes. `fonts.rs` builds a second collection for the monospace lookup.
- Editions and the project file: `slint-project.json` names the main file and the edition, and the LSP finds it by walking up from any `.slint` file to the editor's workspace root (an editor opened on the repository or on the crate reaches it; one opened on `ui/` alone doesn't). The viewer takes the project file or its directory; a bare `.slint` path compiles without the edition. `CompilerConfiguration::with_edition` sets it from the build script instead.
- The testing backend gains `ElementQuery::match_accessible_label()`; the tests match on `accessible-id`, which still has no matcher, so `support::find_by_accessible_id` stays.
- `WinitWindowAccessor::dispatch_winit_window_event()`: the key remaps dispatch Slint keys, not winit events, so no caller.
- `@deprecated`, `TextInput.has-selection`, `StyledText.selectable`, `backdrop-blur`: no use here.

**Behavior changes to check.**

- Edition 1.19 has four gates in the compiler: an element created with `if` or `for` counts toward its parent's size; a wrapping `Text` with a width of its own inside `if` or `for` is measured at that width ([#14705](https://github.com/slint-ui/slint/issues/14705)); a property set by only some states keeps its default in the others; and a binding loop inside a component is an error. The UI has no `states` blocks and compiles without loop diagnostics, so the two sizing rules are what can move: the panes create rows and cards with `if` throughout, and the wrapped texts are the help bubble, the toast's title and message, the schema form's helper and error texts and the dialogs' prompts.
- The winit backend applies a launcher's startup token from the environment and clears the variables ([#14360](https://github.com/slint-ui/slint/pull/14360)), after the window-attributes hook has run, so an environment token replaces the one our D-Bus `activation-token` hook set when both exist. A D-Bus-activated process has no environment token, so the hook's path is unchanged in practice.
- New warnings: a text input nested in an element whose accessible role is itself `text-input` or `spinbox` exposes the same text twice (`ThemedSpinBox`'s input tripped it; the bump sets `accessible-role: none` on it, as `LineEditField` already does, and the spin box's accessible value becomes the field's text so it stays what a reader sees), and a value with no effect at the end of an `if` branch. The gates deny warnings.
- The compiler gains an info level with three sites: a binding to a property's default value, the missing-edition notice, and the experimental-features notice. `slint-build` drops infos; the 1.19 viewer's `--check` and the LSP show them.

**Dependencies.** fontique moves to 0.12 with Slint (Dependabot #240 closes with the bump). Slint's `gettext-rs` moves to 0.8, retiring the duplicate-version skip and the advisory note in `deny.toml`. `pin-utils` stays, through `spin_on` under `slint-build` and `slint-macros`, so its advisory ignore stays. Slint's clipboard (`smithay-clipboard` 0.7) is on SCTK 0.20 while winit 0.30 keeps SCTK 0.19, so `smithay-client-toolkit`, `calloop` and `calloop-wayland-source` are duplicated until the winit upgrade; `deny.toml` skips the 0.19 side.

**Gates while the release is pending.** The Nix package build needs an output hash per git source; one entry in `package.nix` would turn the Nix CI jobs green on the pre-release, and it is left out on purpose, so that something in CI stops a merge before the release. The jobs stay red until 1.19.0 is on crates.io and the three `[patch.crates-io]` entries go; `deny.toml` allows Slint's repository as a git source for the same window, so `just check` and the audit job stay meaningful. The dev shell's `slint-viewer` and `slint-lsp` build from the same revision, since a tool older than the edition can't read the project file; `slint-tr-extractor` stays on nixpkgs' release, since it only walks the `.slint` files for `@tr` strings and the UI uses no 1.19-only syntax. The 1.19 viewer's `--check` over the project reports 80 infos, every one "set to its default value" (`alignment`, `spacing`, `width` and `height` mostly; 27 in the profiles pane, 21 in the widgets), and no warnings.

## Decisions

1. **The edition lives in the project file, and the build script compiles the project file.** `crates/tisvlay-gui/slint-project.json` holds `edition` and `main`; `build.rs` passes its path. *Why:* the LSP and the viewer read the same file, so the editor's preview, the headless checks and the build agree on the edition and the main file, declared once.
2. **The pre-release branch now, the registry at release.** The pins read `=1.19.0` and `[patch.crates-io]` points the three Slint crates at one revision of `pre-release/1.19` (a `rev`, not the branch, so a `cargo update` can't move the compiler under the pin); the dev shell's viewer and LSP build from the same revision. The PR stays a draft until 1.19.0 is published and the patch section is gone. Since step 8 the revision is on a fork, `ruffsl/slint`'s `ruffsl/v1.19-changed-init`: the pre-release branch plus the one commit of slint-ui/slint#14927, which upstream hasn't merged. *Why:* the release is days away by Slint's history (its calls for testing precede releases by one to two weeks), so the work starts now and merges on the release, with CI's audit and Nix jobs as the gate.
3. **Only the reach scope's desktop branch goes.** `LineEditField`'s `reach` scope also carries couch mode's edit-on-Return, where the input is disabled until Return so the on-screen keyboard doesn't rise at every field a remote steps past. On a desktop the scope takes the Tab and forwards focus to the clipped input, which 1.19 reaches itself; it is also where the desktop reports the focused row to `Nav` synchronously from `focus-gained`, and the component's `forward-focus` target. The report moves to the input's `changed has-focus` (a `TextInput` has no `focus-gained`), which is deferred: the Rust key walks drain it with the Tab's dispatch, so they still read the row. `forward-focus` stays on the scope, which is disabled on a desktop while the input has focus, so a `root.focus()` would walk on; nothing calls it (the component's own `take-focus` and `focus-input` are the entry points), and the step's test pins that. `leaving-backwards` stays too: couch mode's Shift+Tab out of an editing input still needs it. *Why:* the fix covers one of the scope's two reasons, and the other two roles move or are already unused.
4. **The select flyout's cursor row keeps itself in view with `ensure-visible(instant)`, and the opening position keeps its binding.** A row calls it from `changed is-cursor`, so a keyboard step reveals the cursor, and so does a step after a wheel scroll in the flyout, which drops the `content-y` binding today and leaves later steps unrevealed. The binding stays for the open-at-current case: a select opening on a value past `max-visible` makes its row the cursor in the creation pass, where `changed` doesn't run and the layout isn't there for `ensure-visible()` to read. *Why:* the API covers the moving case exactly and fixes a latent bug there; the opening case is one declarative line that the API would need a deferred timer to match. `instant`, not `smooth`: the flyout tracks a key press, and `smooth` runs a spring the tests would have to drive.
5. **The reveal margin stays as it is.** `ensure-visible()` brings an item edge to edge, which Slint's focus handling already does; the margin around the stop is the GUI's own and keeps its code. *Why:* no API change covers it.
6. **The shared font collection isn't adopted.** `fonts.rs` keeps its own collection for the monospace lookup. The case for it is real: one collection would give Slint's text and our lookup the same fontconfig view, and spare a second system font scan. *Why not:* sharing needs `unstable-fontique-012`, a second preliminary feature renamed at every fontique bump next to `unstable-winit-030`; both scans already run off the UI thread (Slint's in the background since 1.19), and the two views come from the same fontconfig. The coupling buys nothing a user would see.
7. **The compiler's diagnostics are acted on, warnings and infos alike.** The gates deny warnings, and an info the 1.19 tools report is fixed where its suggestion is right; the ones left standing are listed in Deviations with the reason. *Why:* the new level is a review of the `.slint` files for free.
8. **Upstream issues aren't filed from this train.** The hold's condition (TisVlay tried on 1.19) is met by it; the drafts wait for the maintainer's review. *Why:* filing is the maintainer's call. The maintainer filed three on 2026-11-11 (slint-ui/slint#14892, #14893, #14894), and step 8 takes their fixes.

## Steps

Each step is a commit on `feat/slint-1.19`, passing `just check`. The KDE neon VM is down for this train, so the layout checks use the dev shell: the 1.19 `slint-viewer`'s `--check` and `--screenshot` against the project, and the GUI's own live preview (`GUI_LIVE=true`) on the desktop.

1. **The bump.** The three pins at 1.19.0 on the pre-release branch, the lock, fontique 0.12, the project file with the edition, the spin box's accessible role, the `deny.toml` entries, the `unstable-winit-030` audit paragraph, and the dev shell's viewer and LSP from the same revision. *Verified by:* `just check`; the two tools build and report 1.19.0; `slint-viewer --check` on the project compiles the UI with the edition.
2. **The layout under the edition.** One binary, two editions: the 1.19 viewer renders the project (edition 1.19) and the same files with `--edition 1.18`, headless, and the renders are diffed pixel for pixel, so renderer changes between the compilers (the text-jitter fix, drop shadows, gradients) don't blur the edition's effect. The main window, Settings, About, Profiles and a TV detail at two heights, with a TV fed through `--load-data`, were identical before this plan was written. What the root properties can't populate (the profile editor, the pairing wizard, the dialogs, the toasts, the help bubble, and so the wrapped-text sites) is checked in the GUI itself against the mock backend, where the live preview's deleted-parent crash is also tried first (the Edit pencil under `GUI_LIVE=true`), so the pass knows whether it runs compiled with the MCP server instead. *Verified by:* the renders match, or each difference is listed in Deviations as intended; the live pass lists the states it covered. *Done (2026-11-09):* every render matched between the editions. The live pass ran on the dev stack with a mock TV, driven through the Slint MCP server: the system and user profile editors with their selects and spin boxes, a pinned help bubble and its Escape, the new-profile name dialog, the delete-profile and remove-TV confirm dialogs, the pairing wizard's discovery step with the vendor select open and its configure step with the schema form's helper texts, and a TV detail from its status card to its danger zone, all laid out as before. The interpreter survived the Edit pencil under the live preview, so the deleted-parent crash is gone. Not exercised: a toast (no safe trigger on this stack); its texts are the help bubble's kind. Seen but not 1.19's: the TV detail's "From the TV" labels clip at the form row's fixed label column, and the profile header's "Used by" list clips at the badges with four TVs.
3. **The reach scope's desktop branch goes** (decision 3), with the `slint-gotchas.md` entry and `docs/gui/remote-navigation.md`'s lesson on the field below the fold rewritten for what's left. *Verified by:* the navigation tests still Tab into a field below the fold and leave it backwards, and read `Nav`'s reported row after the Tab, not only the typed text; a test that a `root.focus()` on the field lands in the input on a desktop and on the stop in couch mode.
4. **The select flyout's cursor row keeps itself in view** (decision 4). *Verified by:* a test that opens a select of twelve on its eighth value and finds the cursor row's rectangle inside the flyout's before any key, then steps to the last option and picks it; a test that scrolls the flyout by wheel, steps, and finds the cursor row inside the flyout again. *Done (2026-11-09):* both tests pass; the wheel test steps Up to the first row, since the wheel leaves the pointer on a row and the rows' hover handler makes that row the cursor, which is the existing behavior. A scratch component against the same Slint revision confirmed `ensure-visible` scrolls a ScrollView after a wheel replaced its `content-y` binding. The testing backend's element queries skip clipped elements, so "inside the flyout" is "found at all, and within its rectangle".
5. **The compiler's infos** (decision 7), from the 1.19 viewer's `--check` of the project. *Verified by:* the check reports nothing beyond the infos Deviations lists. *Done (2026-11-09):* all 80 bindings removed, the check reports nothing, the GUI tests pass and the headless renders are byte-identical to the ones before. Two comments that explained a removed binding went or were reworded. The one judgment call, a `dismissable: true` written next to a dialog's `false` for contrast, went with the rest: the neighbor's `false` says what differs.
6. **The gotchas re-checked on 1.19.** `Timer.restart()` inside an inlined component and `absolute-position` read in a geometry change handler, with scratch components; the interpreter's verdict from step 2; and the startup token's two paths, a launch from the `.desktop` file and one through D-Bus activation, each landing one focused window. Each entry in `slint-gotchas.md` (whose header dates the rest to 1.18.1) and the live-preview concern is kept, rewritten or retired by the result. *Verified by:* the verdicts recorded in the docs. *Done (2026-11-09):* the live-preview concern retires, the interpreter having survived the Edit pencil in step 2. The `Timer.restart()` entry stays as a caution: a minimal component with a timer compiles on 1.18.1 and 1.19 alike, so the inlining shape that crashed isn't pinned down by the probe, and the workaround costs nothing. The `absolute-position` entry stays too: a probe reading it from a width change handler didn't panic on 1.19, but the overlay's read from a post-layout tick is the robust form regardless. The startup token's two launch paths weren't run: the dev build isn't started by a launcher here, and the packaged GUI is the previous release; it's a manual check for the first 1.19 package on a desktop.
7. **Three findings from the live pass**, taken into the train by the maintainer on 2026-11-09 though none is 1.19's: after a TV in the middle of the list is removed the selection index stays, so the next TV's detail opens with its own Remove button where the pointer was (the selection clears or moves to the previous row instead); the TV detail's "From the TV" labels clip at the form row's fixed label column; the profile header's "Used by" list clips behind the badges once four TVs use the profile. One `fix(gui)` commit each. *Verified by:* a test that removing the middle TV of three leaves no detail open or the previous TV's; headless renders of the TV detail and of a profile used by four TVs with the texts whole. *Done (2026-11-09):* the removal keeps the list's index semantics (the next TV takes the slot) but the detail instance, which the in-place list update hands the next TV, scrolls back to its top when its TV changes, so nothing destructive sits under the pointer; a test scrolls a detail, removes the TV before it and finds the next TV's Power button at the top. The form row's label wraps within its column (a render shows the three labels whole, on two lines). The "Used by" names sit on a `FlexboxLayout` that wraps them onto further lines, in place of the sideways-scrolling Flickable; a test lists four TVs at the desk size and finds every name in view inside the window. A fourth finding, from the maintainer driving the rail and the lists by key: the selected fill arrived a frame after the focus ring, on the sidebar items and on the list rows alike. Both animated their background over 150 ms while the ring snapped, and on a frame that also rebuilds a pane the fade collapsed into a visible step. The selected fill snaps with the ring now and only the hover keeps its fade, on a layer of its own under the ring. No test reads a paint; the headless renders are unchanged, and the maintainer's eye on the live preview is the check.
8. **The three fixes to the issues filed from the TV-navigation train.** The Menu key's release no longer opens a context menu (slint-ui/slint#14902) and a refused `focus()` no longer walks into hidden items (slint-ui/slint#14907), both on `pre-release/1.19`; a change made in `init` reaches `changed` handlers (slint-ui/slint#14927), open upstream and carried by the fork revision of decision 2. The workarounds go: the shell's capture of the Menu release, the dialogs' `enabled: open` on their scope, buttons and field, and `Focusable`'s `init` that ran `focus-in` for a control created with focus. What stays: the guards on a programmatic `focus()` whose target may be disabled (the walk still moves focus, to a visible stop), the key-count focus recovery (focus is still cleared when the focused item goes), and the row report in `focus-gained` (the walks read it in the same pass). *Verified by:* the reproducers behind the three issues against the fork revision; the GUI tests, which hold a regression test for each workaround. *Done (2026-11-14):* the reproducers report all three fixed, and the GUI tests pass before and after the removals.
9. **The registry swap**, when a 1.19 release publishes with step 8's three fixes; if 1.19.0 ships without slint-ui/slint#14927, the swap waits for the patch release that has it, or `Focusable`'s `init` comes back with the swap. Every temporary piece goes in one commit: the three `[patch.crates-io]` entries and their comment in the root `Cargo.toml` (the lock re-resolves to the registry); `deny.toml`'s `allow-git` entry for Slint's repository and the sentence about it in the `[sources]` comment; `flake.nix`'s `slintSrc` and `slintCargoDeps`, their comment and the two `inherit` arguments; `packaging/nix/slint-viewer.nix` back to `fetchCrate` 1.19.0; `packaging/nix/slint-lsp.nix` to `fetchCrate` 1.19.0 (the file itself goes when nixpkgs' slint-lsp reaches the pin); the "until 1.19.0 is on crates.io" sentence in `docs/concerns/slint-unstable-winit-030.md`'s pin section. Dependabot #240 closes. *Verified by:* the release isn't the branch revision this plan was written against (the branch takes fixes until the tag), so `just check` and step 2's render diff run again on the registry crates; the audit and Nix CI jobs green; `nix flake check`; no match left for `pre-release/1.19` or `slintSrc` in the tree.
10. **Docs, and retire the plan.** The 1.19 findings worth keeping move into `docs/concerns/slint-gotchas.md` and the concerns they touch, and `.claude/slint.md`'s tooling notes follow the project file; the ComboBox concern, the accessibility idea and `docs/testing.md`'s GUI testing section stand as they are, their trackers being open; the idea and concern indexes follow; the plan file is deleted.

## Deviations

- **Step 3:** the component lost its `forward-focus` instead of keeping it on a scope that is disabled on a desktop. Nothing called `focus()` on a field (the ways in are `take-focus` and `focus-input`), and without `forward-focus` such a call doesn't compile, which pins the invariant harder than the runtime test the step planned. The input already reported its row to `Nav` from its `changed has-focus`; the scope's synchronous report stays for couch mode, and a test reads the row after a desktop Tab.
