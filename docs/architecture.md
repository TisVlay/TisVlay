# TisVlay Architecture

The current (v0.3.0+) architecture: a **bevy_ecs world** owns every daemon state machine, and **zenoh over Unix sockets** is the IPC surface. This document is the durable successor to the plan documents that drove the rewrite (the spike and parity plans, now retired to git history; [design.md](design.md) remains for the retired served-D-Bus stack ≤ v0.2.0). Consumed desktop D-Bus (logind, ScreenSaver, ksni tray, notifications, `org.freedesktop.Application` GUI activation) remains zbus; nothing serves D-Bus anymore.

## Process inventory

| Process | Role | Zenoh sessions |
|---------|------|----------------|
| `tisvlay-daemon` | System service: world + backends + zenoh bridge, store, discovery, watchers | peer, listens on the system socket |
| `tisvlay-session` | Per-user gateway: user profiles, lock/unlock + idle dispatch | client → system socket; **router** listening on the user socket |
| `tisvlay-tray` | ksni tray over a live mirror, desktop notifications, settings service | connect-only peer → system; supervised **client** → user socket (it serves there) |
| `tisvlay-greeter` | Login-greeter idle client (`ext-idle-notify` → `greeter/idle`) | connect-only peer → system socket |
| `tisvlay-gui` | Slint settings window | connect-only peers → both sockets |
| `tisvlay` (CLI) | Pure zenoh client | client → both sockets (one-shot, fails fast) |

The daemon, session, tray and greeter aren't binaries of their own: each runs from the CLI's `tisvlay` binary as `tisvlay service <name>` (the service crates are libraries with a `service` module holding their flags and entry point). Their systemd units and journal identifiers keep the names above. One binary links zenoh, tokio, zbus and the SDK once instead of five times: under the `dist` profile the CLI and the four services went from 45.4 MiB as five binaries to 17.0 MiB as one. The GUI stays separate because it alone links Slint and the system graphics libraries (fontconfig, freetype, libpng and others), which every CLI call would otherwise load.

## Two-socket topology

Zenoh peer routing is transitive: one connected mesh would let any client read any key, so separate sockets alone don't reproduce D-Bus's session isolation. The design is an **application-level gateway**:

- **System socket** (`/run/tisvlay/zenoh.sock`, 0660, group `tisvlay`): the daemon's peer listener. Owns `tisvlay/<site>/**` except the `user/` subtree.
- **User socket** (`$XDG_RUNTIME_DIR/tisvlay/session.sock`, 0700 runtime dir): the session service's **router** listener. Owns `tisvlay/<site>/user/**` — profiles, per-TV assignments, its liveliness token. Nothing routes between the session service's two zenoh sessions except explicit application logic, so user-private keys physically never reach the system peer. The session's split (user router + system peer) stands on **isolation alone**, not on `single_link`: a single session bridging both sockets would transitively route the two key spaces (user leaves could read `tv/**`/`manager/**`; the daemon could see `user/**`), so even with the serve-side law fully corrected, merging them defeats the gateway.
- **Clients open two sessions**, one per socket, and route by key: `user/**` on the user session, everything else on the system session. A zenoh *client* keeps a single link (`single_link: true` — a multi-endpoint connect list is failover, not fan-out), so the *clients'* two sessions are structural, not stylistic (a distinct rationale from the session service's isolation split above).

### Link modes and the serve-side law

Every *consuming* link is a **connect-only peer** (`mode=peer`, empty listen, `exit_on_failure: false`): the session opens before any link exists, dials the hub forever, and liveliness tokens are the availability signal (the `NameOwnerChanged` equivalent). This buys start-order freedom — any client can boot before the daemon.

The law learned empirically: **a connect-only peer leaf cannot fan out what it serves.** Queryables, liveliness tokens, and cached publishers it declares are invisible to *other* leaves re-broadcast through a hub (both peer-mode and router-mode hubs) — but the **directly-dialed hub itself does observe them** (verified on zenoh 1.9.0's ("Longwang", 2026-04-16) Regions routing rework, which is where the observation changed — the law was accurate for 1.0–1.8; the rule governs third-party fan-out, not observation by the endpoint you dial). So anything that must serve *to other leaves* uses a **client-mode link into a router** (routers relay client-declared entities), supervised with a fail-fast open + retry loop so it re-serves after a hub restart — hence the user socket is a router and the tray's settings service is a supervised client link. Where only the dialed peer needs the signal, a connect-only peer suffices: the session declares its `alive/session` token on its system link and the daemon (the peer it dials) observes both the PUT and the crash-time DELETE.

## Key space

[`tisvlay-protocol`](../crates/tisvlay-protocol/src/lib.rs) is the single vocabulary source: key constructors (`keys::*`), payload structs (the serde wire payloads, which the world stores as components wrapped in its `State<T>`, so the protocol crate has no bevy dependency), typed `WireError`, and session bootstrap configs. The shape by prefix, all under `tisvlay/<site>/`:

```
tv/<uuid>/state/{power,volume,input,backlight,link}   cached pubs (state fan-out)
tv/<uuid>/meta/{identity,config,vendor}               cached pubs (name+primary descriptor, managed/profile, display rows)
tv/<uuid>/rpc/<verb>                                  queryables (set-*, power-*, get/update-config, re-pair, …)
tv/<uuid>/progress/power                              power-cycle phases (wol_sent → connecting → connected/failed)
pairing/<uuid>/progress                               pairing phases per attempt (awaiting_tv → complete/failed, typed codes)
profile/system/<uuid>                                 cached pubs, PUT/DELETE lifecycle
profile/rpc/<verb>                                    create, update, duplicate, delete, defaults, effective
manager/vendors[, /<id>/schema]                       vendor catalog + pairing-form schema queryables
manager/rpc/<verb>                                    add-tv, pair, discover[-start/-stop], enrich, info, …
discovery/<session>/found/<id>                        streaming findings + alive/discovery/<session> token
event/session/<name>, event/connect-failed            observability taps
greeter/{idle,timeout}                                greeter idle events + published timeout
stream/state                                        stream fact mirror (cached pub; daemon hydrates → world gate)
alive/{daemon,session,…}                              liveliness tokens (session = presence on its system link)
--- user socket only ---
user/profile/<uuid>, user/profile/rpc/<verb>          user-profile catalog + CRUD
user/tv/<uuid>/profile                                per-TV user-profile assignment
user/stream/state, user/stream/rpc/<verb>           stream fact (cached pub) + manual arm/disarm verbs
user/tray/settings, user/tray/rpc/<verb>              tray notification switches (cached pub) + get/update/test/info/reload
user/alive/{session,tray}                             per-user service liveliness
```

Secrets never leave the daemon in a reply (a client sends the client key only in `add-tv`/`pair`/`update-config` requests): `get-config` redacts through the vendor `config_schema` visibility tags (`Secret` fields dropped daemon-side). Nor do they reach `Debug`: typed credentials are `tisvlay_core::Secret`, and the vendor config and the requests carrying it print key names only.

### Typed rpc endpoints

Every rpc is declared once, in [`tisvlay-protocol`'s `endpoint` module](../crates/tisvlay-protocol/src/endpoint.rs), as a marker type implementing `Rpc`: its key, its request type and its response type. A `Unary` rpc answers once (`REISSUE` marks the reads safe to re-issue when a matched query closes without a reply); the one `Streaming` rpc, `discover`, answers once per finding until its window closes. Bodies are JSON on the wire.

- **Families:** a small macro invocation per verb-shaped family (`manager`, `profile`, `tv`, `user_profile`, `user_stream`, `user_tray`) generates the markers and the family's `Call` enum, one variant per rpc carrying its decoded request. The vendor catalog, keyed by vendor rather than verb, is declared by hand.
- **Clients** call `Caller::call::<R>(target, request)` (or `call_many::<R>`). The caller holds the site, awaits the querier's matching status, and decodes the reply as `R::Response`: a reply that doesn't fit is an error, never a silent null.
- **Servers** declare each family's queryable on `Incoming::wild(site)` and receive every query with `Incoming::receive(site, query)`, which parses the key, decodes the body and refuses what fails (`unknown-rpc` for a key naming no rpc, `bad-request` for a malformed body). They match the `Incoming` enum exhaustively: each variant carries the decoded request and a `Responder<R>` typed by that rpc. Answering (`ok`, `err`, or `answer(Result<R::Response, WireError>)`) consumes the responder, so a missing handler, a wrong body type, a reply of another rpc's type, or a second reply doesn't compile, and a responder dropped unanswered logs a warning. The streaming `discover` sends one reply per finding and `finish`es. Each gate has a `compile_fail` doctest next to a passing twin (`endpoint::gates`).
- **World-answered rpcs** (add-tv, pair, profiles, the per-TV commands) carry a typed `Reply<R>` token in their `Command`: the bridge files the responder's query and gets back a `Reply<R>` of the same `R`, and replying takes `R::Response`, so the world's replies are type-checked too. The paths several rpcs share (power and screen dispatch, the backend's deferred acks) carry an erased `AckReply`; refusals an `AnyReply`.
- **`RpcError`** is a call's outcome when it didn't end in a typed reply: the service's `WireError` refusal (§ Error model), or the caller's own `Unavailable`, `Timeout`, `NoReply`, `Transport` or `Undecodable`.
- **No wire compatibility:** every client ships with the daemon, so requests decode strictly. A newer daemon and an older user service (until re-login after an upgrade) may refuse each other; that window is accepted rather than coded around.

**Why no rpc framework.** Typed endpoints are the idiomatic Rust shape (postcard-rpc's `Endpoint`, Bitwarden's `RpcRequest`, Fedimint's `TypedApiEndpoint`; the server-side request enum is tarpc's, minus its transport). The frameworks themselves don't fit: zrpc (ZettaScale's zenoh rpc) is alpha and brings its own encoding and key layout, which break the zenoh laws below; tarpc needs a connection-shaped transport, which zenoh query/reply isn't; gRPC would replace zenoh outright. zenoh's own typed-queryable proposal ([eclipse-zenoh/zenoh#2510](https://github.com/eclipse-zenoh/zenoh/issues/2510)) would slot under this layer if it lands.

### Error model

- **Refusals:** a server refuses an rpc with `WireError { code, message }`, and servers build every refusal through `WireError`'s constructors (the fields stay public for clients reading them). `ErrorCode` is one enum in `tisvlay-protocol`, kebab-case on the wire and shared by every server and client; a code the client doesn't know fails the call as `Undecodable` rather than falling back. The `invalid-field` message is `"<field>: <reason>"`, parsed by `invalid_field_parts` beside its constructor so forms can mark the offending row.
- **The client SDK** (`tisvlay`) returns one `#[non_exhaustive]` `tisvlay::Error`, its variants named for what the caller can do: `Rpc { code, message }` (the service refused), `Unavailable` (not running, or not reachable yet), `Timeout` (no answer; a write's outcome is unknown), `Transport` (the local link, with its cause in `source()`), `Protocol` (a reply that didn't decode) and `VersionMismatch` (the service runs a release it can't talk to; see § Compatibility). Each names the `Service` it was talking to. `rpc_code()` and `invalid_field()` are the branching helpers; `RpcError` and dependency errors stay out of the signatures, boxed as sources.
- **Pairing and dial failures aren't refusals:** they arrive on the progress keys as a typed `FailureCode` in the progress detail, whose wire tokens are namespaced (`pairing.*`, `device.*`) ([typed-failed-reason-payload.md](ideas/typed-failed-reason-payload.md)).
- **`anyhow` lives at the edges:** binaries and binary glue (`tisvlay-runtime`, the service crates' library halves). The GUI lifts SDK errors into `anyhow` where it only reports them and renders the whole cause chain in its error slots.

**Why this shape.** Libraries expose concrete error types and keep dependency errors as boxed sources, never `anyhow` ([d34dl0ck, May 2025](https://d34dl0ck.me/rust-bites-designing-error-types-in-rust-libraries/index.html)). Enum and opaque-struct shapes are both current ([iroh, Aug 2025](https://www.iroh.computer/blog/error-handling-in-iroh); std::io and reqwest); the SDK takes the enum because its callers branch on the outcome, and `thiserror` is enough for IPC outcomes.

## The world

[`tisvlay-world`](../crates/tisvlay-world/src) holds a bevy_ecs `World` owned by a single **reactor** task. All async I/O lives in tokio tasks outside the world; the world mutates only at sync points:

1. The reactor batches its inbox (`InEvent`: commands from the bridge, backend facts, watcher events, pairing updates, ticks). Ticks apply first, so the whole batch sees one clock.
2. Client commands apply one at a time, in arrival order. Each runs its handler as a one-shot system (`World::run_system_cached_with`), whose `Commands` flush before the next command runs, so every command sees the ones before it. The reactor's match over `Command` is exhaustive, so a command without a handler doesn't compile, and the reactor answers each reply from the handler's returned result.
3. The batch's facts become bevy messages, and one `Schedule` run processes them: ingest systems → dispatch/reconcile → derive/publish tail (deterministic ordering via a chained schedule).
4. Drained effects leave the world: `WireEffect` (publish/delete/reply) to the daemon's zenoh bridge, `Persist` snapshots to the store task, dial spawns as tokio tasks, route-monitor requests to the netlink watcher, device-monitor requests to the device watcher.

Commands are one-shot systems rather than observers on purpose. Observers fit when several independent listeners react to one event, or when code you don't own triggers it. Each command has exactly one handler and only the reactor sends commands, and a missing observer fails silently: the trigger reaches nothing and the caller times out.

Identity components are immutable and own their indexes through component hooks. `TvId`, `ProfileId` and `PairingFor` index their entity on insert and unindex it on discard, so `TvIndex`, `ProfileIndex` and `PairingIndex` can't drift from the live entities; debug builds assert that after every step. Removing `TvId` (despawn included) also deletes every key the TV published and releases its route and device monitoring, and removing `ProfileId` deletes the profile's key, so no removal path can forget either.

Payloads are components, each wrapped in the world's `State<T>` — `publish_changed<T>` turns bevy change detection directly into wire publishes, and `derive_link_state` derives `Link` from world structure (`connected ⇔ ConnectionHandle exists`). Connection lifecycle is marker components: `PendingConnect` (the **single dial gate** — every recovery path funnels through `redial()`), `Reconnecting` (dial in flight), `RetryAt` (backoff), `Parked` (what the connection depends on went away: carrier, route or device node), `AwaitingDependency` (dial deferred on a known absence), `HeldWake` (since when a wake has waited on one), `ConnectionHandle` (live task channel; dropping it closes the connection — RAII, no drain layer). Every dial is numbered (`DialSeq` → the TV's `LatestDial`) and every event its task sends carries that number; events from a superseded dial are dropped (rpc replies excepted, since they route by reply id), so a re-pair — which clears `Reconnecting` to spawn its verification dial at once — can't be settled by a dial still in flight on the old credentials. A network TV that goes down stays down until asked; only carrier/route restore redials parked TVs. A local-device TV (one whose connector names a `local_device`, CEC's `/dev/cecN`) also redials after one backoff when its connection drops, since that connection survives standby, and its device's return redials it at once. **Dials are deferred on a known absence of what they depend on**: a `MonitoredInterface` reading `Some(None)` (no route) or a `DeviceAvailable(false)` (no device node, from the [device watcher](watchers/devices.md)) defers the dial with the attempt budget reset — attempts count only dials whose dependency was there (a failure whose dependency vanished mid-flight returns its attempt but keeps the backoff, bounding flap) — and the dependency's return resumes it structurally through the same reconcile pass. A pairing verification dials through, so a re-pair fails with its reason instead of waiting. Component absence is load-bearing: no route resolution can precede a network TV's first dial (monitoring is requested by the dial spawn), so first dials and fixtures dial; a local-device TV's first dial instead waits for the watcher's first report when one is attached. A device that exists but can't be opened keeps a local-device TV retrying past its budget, doubling to a 60 s gap; every other failure keeps the three-try budget. **A held wake is bounded**: a wake deferred on a missing dependency publishes `awaiting_network` or `awaiting_device`, expires after 60 s into a plain reconnect (which never powers the TV on), and is cancelled by a newer off intent (a power-off, or a screen-off where the screen is emulated as power), so a dependency back hours later can't turn the TV on. `Link.waiting_for` reports the absence to clients, read from the facts rather than the markers, so a parked TV says it too.

Screen actions ride a reliable tier with `DispatchVerify` as the **single screen-intent latch**: send, then verify against the cached power state after the backend's verify delay, retry within the budget, and escalate an unmet `screen_on` to the power path (in place for standby-reachable transports, wake dial otherwise). The latch survives a wake-driven teardown — verification defers while a dial is pending, and the reconnect re-asserts the panel and restarts the clock — with an `escalated` flag capping every dispatch at one wake dial, so a TV that ACKs dark can't ping-pong wakes. Entry points that route `screen_on` onto the power path instead of erroring or retrying into a void: a wake-needy cached power state on a live link (the pre-flight — `PowerState::needs_wake_preflight()`, where `Unknown` counts only for network transports since a standby-reachable TV reads `Unknown` while genuinely on), and a disconnected wake-capable TV (the elevation — acked when the dial arms, like `power-on`). The power path itself routes by transport: standby-reachable buses wake in place over the live handle, network transports spend the dispatch's wake dial (LG has no in-band `power_on` — WoL is the only wake). A `screen_off` while a dial is in flight latches and lands on the reconnect (the locked-idle timer racing a boot wake); a disconnected `screen_off` with no dial is a satisfied no-op. Exhausted intents die observably on the `event/dispatch-failed` key.

Primary-input restore rides the same shape: an event mapping can carry a `restore_input` modifier (string-or-table profile form, stock-on for the session-start wakes), which the resolving side - the session for user events, the world for system events - places on the `SetScreen`/`PowerOn` payloads as **resolved intent**; manual clients never set it, so manual actions are input-neutral by construction. A restore-flagged dispatch with a configured `primary_input` arms `DesiredInput`; the `reconcile_input` drain waits through dials, requires the advertised `INPUT` capability (CEC sheds the intent structurally - its wake already selects the adapter's port), compares the mirrored input state, re-sends within the verify budget, clears on first compliance, and fails onto `dispatch-failed`. A manual `switch-input` cancels any pending intent - the user is authoritative. The `automated` gate itself is profile policy (root parity): `automate_when` resolves through the assigned-profile - default-profile chain with an `Always` floor, and `meta.automate_when` is a read-only projection of that resolution - there is no per-TV storage. A second, orthogonal gate rides the same dispatch: while a TV is in the world's `StreamArmed` set (fed by the `stream/state` mirror), an event whose resolved action has `while_streaming = false` is suppressed — a pure gate (suppression only, never origination), additive to `automated`, that keeps a stream's injected input from waking the panel for an empty room. The stock floor gates wake-ish events and exempts off-going ones, and it is per-event invertible; see [streams/detection.md](streams/detection.md).

Two invariants with their own history: **managed gates automation, not connectivity** (unmanaged TVs stay connected for state and manual control; only profile-driven actions stop), and **pairing terminals gate on the first real dial** (`PairVerifying`: `complete` publishes only once the TV actually connects; a fresh enrollment that fails its first dial rolls back entirely). That verification dial is also the one pair-time read of the device-reported link MAC (`SpawnConnect.pairing` → `TvConnection::get_link_mac`, bounded at 3 s), which works where ARP can't — a TV on a routed or VLAN-isolated segment. An unset `mac` is filled in canonical form and the config-derived facts refresh at once, so the TV is wakeable without waiting for a dial; a configured `mac` is never overwritten. The daemon compares the two, and the `complete` sample carries the outcome (`LinkMacReport`: filled / matches / differs) for clients to render — the GUI's finished step offers the reported MAC on a mismatch. Transport characteristics (`TransportTraits`, `supports_wake`) are config-derived by the reactor ahead of every dial — never inferred from dial outcomes.

Same-batch hazard, facts only: a schedule system's `Commands` (and the hooks they trigger) land when it finishes, so a fact system reading `MessageReader<InEvent>` sees pre-flush state for every message in a batch. Same-key fact streams collapse to the latest per key before acting (`apply_route_resolutions`, `handle_carrier_events`), and the fact systems that despawn mid-batch (`apply_backend_events`' rollback, `apply_pairing_updates`' terminals) track what they ended so later messages skip it. Commands don't share the hazard: each flushes before the next.

Reply-side backpressure is load-bearing: backend commands ack on TV completion (`BackendEvent::CommandDone`), not on enqueue — this is what makes the tray's `Coalescer` "latest wins" actually bound queue depth.

The daemon supervises its core tasks. `Stack::run_until` watches the reactor, the zenoh bridge and the store writer alongside ctrl-c and SIGTERM. A core task ending — a panic in a world system unwinds the reactor, after the world's fallback error handler logs the failing system by name — withdraws liveliness, stops the world so the store writer's channel closes, waits for the pending snapshot to flush, and exits non-zero for systemd to restart the daemon from its store. A signal takes the same ordered path and exits cleanly. Restarting from the store, rather than carrying on, is deliberate: a panicked system has just broken an invariant.

## Backends

Vendor backends implement four `tisvlay-core` traits and register as one `VendorReg` entry in the daemon — see [backends/implementing-a-vendor.md](backends/implementing-a-vendor.md). The vendor config travels as an opaque `VendorConfig` (a TOML table whose `Debug` prints key names only); the schema's first field is the **primary descriptor** (LG: IP, CEC: device path), used by log lines, the CLI list, the wizard's manual entry, and route monitoring.

## Persistence

The daemon's store is one TOML file (`/var/lib/tisvlay/daemon.toml` packaged, `--config` in dev) holding TVs (with credentials), settings, and system profiles. `snapshot_store` rebuilds the TV and profile table every step and emits a `Persist` effect only when it differs from the last snapshot persisted, so whatever reaches the world reaches the store and derived-only changes never write; the store task debounces and writes durably (`tisvlay_runtime::fs::write_atomic`: a 0600 temp file, fsync, rename, then a directory fsync). Writes go through `write_toml`, which reconciles the new snapshot into the file's existing TOML document, so a hand edit's comments and layout survive wherever their values didn't change (array-of-tables entries match by `id`), and a file that already holds the snapshot isn't rewritten. The reconciled text is parsed back and compared before it's written; a mismatch writes the file fresh instead. A fresh enrollment still verifying its pairing stays out of the store, while a re-pairing TV stays in. Boot applies the store before the reactor runs: `serve` loads it, and `Reactor::seed` makes the loaded snapshot the diff baseline and replays its rows in one synchronous step, so replay writes nothing back and no step ever runs against a half-replayed table. `--seed` applies a bottom-layer config only when the daemon has none, with UUIDv5 content-derived identity so re-seeding never duplicates TVs. The session service persists user profiles the same way under `~/.config/tisvlay/session.toml`.

A hand edit of a state file applies on reload: the `reload` rpc of the daemon, session or tray (the GUI's Reload button and `tisvlay reload` call all three), or SIGHUP for the daemon (`systemctl reload`). The GUI reports the outcome whichever pane is open, since the button belongs to no pane: a toast naming the files that changed, or an app-level banner above every pane (under the access banner) for a file that couldn't apply; a service that isn't running is skipped. A file the service can't parse is reported like a compiler error (see `tisvlay_runtime::fs::read_toml`), in the CLI and the banner alike. The store writer owns the record of what's on disk, meaning the snapshot it last wrote or loaded at boot. `LastPersisted` can't serve, because it holds what the world *sent*, which may still be waiting out the debounce. A reload is a three-way merge:
- the writer reads the file, refusing a missing or unparsable one (never read as empty), and hands over the edit since its record;
- the world (or the session's core) applies only that difference, so changes still awaiting their write survive, and the file wins where both changed a field;
- the edit is validated whole first, then applied through the client commands' helpers;
- the writer holds its writes until the outcome arrives, and a successful reload makes the file its new record;
- before any write, a file that no longer holds the writer's record (an edit nobody reloaded) is moved to `<file>.edited` with a warning instead of being overwritten.

The tray writes every update before answering, so its file only differs after a hand edit, which applies whole.

## Watchers

- **netlink** ([watchers/network.md](watchers/network.md)): carrier transitions per NIC + route-based device resolution (`ip route get` per TV, `MonitoredInterface` scoping) — catches cable pulls and NM software disconnects without NetworkManager. MAC enrichment uses an `RTM_GETNEIGH` neighbor dump (`/proc/net` is invisible under the packaged sandbox's `ProcSubset=pid`).
- **devices** ([watchers/devices.md](watchers/devices.md)): local device nodes (USB CEC adapters) followed over udev's netlink group, so a TV waits for a missing adapter and redials when it's back; a node counts once udev has initialized it.
- **DPMS**: per-connector sysfs watchers auto-spawned by the desktop probe's EDID matching; `--dpms-connector` adds a global-dispatch override. KWin writes DPMS through to the legacy sysfs attribute, so no compositor protocol is needed.
- **logind**: PrepareForSleep → sleep/resume events, under a delay inhibitor released once every live connection has run the commands the event queued (a drain token each connection drops behind them), bounded by logind's `InhibitDelayMaxSec`. Supervised: a dropped system-bus connection (dbus-broker evicts a peer whose user is over its quota) reconnects after 5 s and retakes the inhibitor, like the seat-access watch.
- **Session-side** ([the session crate](../crates/tisvlay-session/src)): lock/unlock and idle, each over the transport the running desktop provides. **Lock** is logind `LockedHint` on the system bus — the one standardized cross-desktop lock-state signal (both kscreenlocker and gnome-shell set it), followed on this user's graphical *seat* session (found by enumeration: the service runs in the user@ manager scope, not a logind session, and keys on the seat — not the session `Type` — so a `startx` login qualifies alongside a display-manager one; the seat's `Active` session wins). It seeds silently at first attach (an auto-login lock arrives with no edge, and re-blanking a parked TV would be wrong) but fires a change that landed during a reconnect gap. This replaced the KDE-only `org.freedesktop.ScreenSaver` `ActiveChanged` interface — never a freedesktop spec, a de-facto `gnome-screensaver`/`xscreensaver` one KDE kept; GNOME's `gsd-screensaver` implements only the standardized idle-inhibit subset, so it never signals lock state. **Idle** is a three-notification watch — a pinned 200 ms lock-wake detector plus per-lock-state idle timeouts (`locked_/unlocked_idle_timeout_seconds`), each gated to its own lock state — over the `ext-idle-notify-v1` Wayland protocol (KWin, wlroots) with an `org.gnome.Mutter.IdleMonitor` D-Bus fallback where the compositor doesn't advertise it (GNOME/Mutter, still true as of GNOME 51). Because those tags gate on *opposite* lock states and `ext-idle-notify` fires `Idled` once per idle period (KWin delivers it even while locked), the lock state is seeded **synchronously** from `LockedHint` before the idle adapter is spawned — the supervised watcher's async seed can land after the first (locked) idle transition, which would drop it against the `is_locked = false` default *and* drop the later unlocked transition once the seed flips the flag, so a session that boots already locked (`LockOnStart`, autologin-then-lock) would otherwise never blank. The login **greeter** ([tisvlay-greeter](../crates/tisvlay-greeter/src)) drives the same two idle transports at the login screen (wayland socket first, Mutter D-Bus fallback), attaching to the DM's greeter-only session target — `plasma-login-wayland.target` (KWin) or `gnome-session@gnome-login.target` (GDM). The session also mirrors per-TV `state/power` for the **idle drift re-assert**: a panel that lights itself while an idle action holds (a stray remote press at the lock screen) gets one idle-timeout of grace, then the idle action re-dispatches — gated on `automated` (so `automate_when: on_primary` users watching another input are never fought), dark intents only, cancelled by any activity or lock transition. Desktop idle timers are edge-triggered and can't see TV-side drift; this closes that gap without making the world enforce persistent intent.
- **Stream detectors** ([streams/detection.md](streams/detection.md)): independent session-side tasks — a manual/hook verb, a PipeWire capture-node watcher, a `BecomeMonitor` portal watcher (attributed by caller exe), a logind graphical-`Remote=yes` watcher, and a Sunshine `/serverinfo` level poll — each reporting a kind-tagged source into an aggregator that crosses live sources with each TV's resolved user profile to compute the per-TV `armed` set. The set publishes as the `user/stream/state` fact and mirrors to `stream/state`; the world's `StreamArmed` resource gates dispatch from it. Detection is the opt-in — nothing arms on a stock desktop.

## Compatibility

`tisvlay-protocol` and the client SDK are published, so clients outside the repo talk to whatever services a distro ships. The contract is **lockstep on semver**: a client talks to services of the same `major.minor`, the rule users already know ("SDK 0.4.x works with daemon 0.4.x"). A distro's daemon patch and the SDK's newest patch still work together.

- **One version, one rule.** `tisvlay_protocol::VERSION` is the protocol's release, and `compatible(ours, theirs)` holds the `major.minor` rule in one place. The services report `VERSION` in their `info` reply (`ServiceInfo.version`). A pre-release is compatible only with exactly itself, since it may still change before its final release; build metadata is ignored. A release that isn't strict semver is a mismatch, never a panic or a guess.
- **The handshake surface is frozen.** The three `info` keys and `ServiceInfo` never change incompatibly: fields may be added, each with `#[serde(default)]` so a newer client reads an older service's reply, and `deny_unknown_fields` is never used, so an older client reads a newer one's. An old client can then always read a new service's version and report a mismatch, instead of `Unavailable` or a decode failure.
- **The SDK enforces it,** per service lifetime. Clients keep their links across service restarts, and the common mismatch is a package upgrade restarting the daemon under a running GUI, so the cached verdict clears when the service's liveliness token goes away and is re-checked on the next call or when the token comes back. A mismatch reaches every path: rpcs fail with `Error::VersionMismatch`, writes wait for the verdict before sending (a `#[serde(default)]` field can decode wrongly with no error), the `Option` mirror reads return `None`, the progress streams refuse to open and drop samples, and `StateWatcher` emits `StateEvent::VersionMismatch` (replayed to a watcher built after the check). `version()` and `config_path()` skip the gate, so they can still report what's running. The GUI shows the mismatch as a window-level banner, and its status indicators (the sidebar dots, the About pane's circles and version chips) render one health per service from the same `compatible` rule: a filled dot is a running service, a hollow one an absent service; green is the same release, amber a compatible patch release, red a release it can't talk to, or offline.
- **The CLI checks for itself:** `status` reports the release and whether it's compatible, and every rpc verb checks the services it talks to first (`watch`, a passive view, doesn't).
- **Not in `Caller`, not in liveliness.** The session's lock/idle dispatch and the tray go through `Caller` directly, and a check there would turn the accepted upgrade window (one re-login) into hard automation failures. Liveliness tokens carry no payload, so a version there would have to go into the key, and exact-key lookups would then see a mismatched service as absent.
- **No shims.** Decoding stays strict, with no skew windows or negotiation, so a protocol change is a minor release. `.config/release-plz.toml` bumps the minor for every `feat` at 0.x too, and CLAUDE.md's commit rule keeps wire-visible changes off `fix`.

**What else was considered:** exact version matching, like tmux, which forces clients to upgrade on every patch; a hand-bumped protocol number, like the Nix daemon, where a forgotten bump is a silent bug; negotiation or skew windows, like Docker and Kubernetes, which need tolerant decoding.

## Deployment and authorization

The packaged daemon runs as the `tisvlay` system user under a hardened unit; it chmods its socket 0660 after bind (the unit runs `UMask=0077`). Access is layered: **`tisvlay` group membership is the durable grant** (`services.tisvlay.users` in the NixOS module; `tisvlay enable-access` is its one-click polkit enrollment) — it covers SSH, remote, headless, and lingering services — and the daemon additionally applies named POSIX ACL grants on the socket: the display manager's greeter group (`--greeter-access`/`--greeter-group` — static for the daemon's lifetime, so the dynamic-userdb GDM greeter can reach the socket) and, **presence-scoped**, each seat's active graphical user (`--seat-access`, default on — `uaccess` semantics for our socket; the entry follows logind's `Seat.ActiveSession`, gated `Class=user` ∧ `Type∈{x11,wayland}` ∧ `¬Remote`). Presence grants are transient by design: switching away removes the entry while active-session arbitration simultaneously suppresses that user's automation; already-open connections persist (the kernel checks at `connect()`). Within the socket there is no per-method authorization — the accepted regression vs D-Bus policy; polkit-shaped gating is a post-parity design if ever needed. Integration detail — per-channel wiring, maintainer-script lifecycle, ACL semantics, verification, and lessons — lives in [packaging/README.md § Socket access & the ACL integration](../packaging/README.md#socket-access--the-acl-integration). Connect-side socket defaults fall back from the dev socket to `/run/tisvlay/zenoh.sock`; listen-side defaults never fall back (a dev daemon must not take over the packaged socket). Sandbox lesson worth remembering: hardening options change what the code can see (`ProcSubset=pid` broke a `/proc/net` parser that worked in dev) — prefer netlink/syscall interfaces over procfs.

## Empirical zenoh laws

Learned the hard way; violating any of these produces silent wrong behavior, not errors:

- Consume-only peer leaves / serve-via-client-link (topology section above).
- Advanced-cache hydration is subscriber-history-only: the cache's queryable sits under a verbatim `@adv` suffix, plain `get`s can't reach it.
- Multi-reply queries (discovery streaming) need `ConsolidationMode::None` querier-side, or consolidation eats same-key replies.
- `timestamping/enabled` must be on daemon-side for cache ordering. Two-sided: a *bare* `.cache()` AdvancedPublisher hard-fails at construction without an HLC (timestamping is per-role — router on, peer/client off), but the project's standard `.cache(…).sample_miss_detection(…)` shape re-sequences by a plain counter *after* `.cache()` set the timestamp mode, so it constructs regardless of timestamping. So no timestamping requirement attaches to a connect-only-peer cached publisher (e.g. the session's `stream/state` mirror the daemon hydrates over its dialed link).
- Publishers guarantee no cross-key sample ordering — tests wait on combined predicates in one drain, never two sequential waits on one subscriber.
- A history subscriber's replayed cache and the live samples racing it have no guaranteed relative order, and per-publisher sequencing never delivers an older sample after a newer one: when a live sample wins, the replayed history behind it is dropped. A key that outlives sessions (pairing progress) therefore can't let watchers infer "theirs" from position — each sample carries its session's `attempt`, returned by the starting rpc, and watchers drain only that attempt.
- A `get` matching zero queryables completes instantly with no reply — and token arrival races queryable-route propagation, so liveliness cannot gate rpcs. Clients therefore gate every rpc on **querier matching status** (`tisvlay-protocol`'s `caller::Caller`: matching ⇒ routable, absent-past-deadline ⇒ `RpcError::Unavailable`) — the pin is `crates/tisvlay-protocol/tests/querier_matching.rs`, and every client (SDK, CLI, tray) rides the shared module.
- **Availability is liveliness, only; rpc outcomes are content.** Presence displays key on liveliness flags; a failed or slow rpc renders as missing content, never as offline. The GUI renders level-triggered: its watch loop drains each burst of state events, then writes every Slint copy from one read of the clients' mirrors, so no stale or reordered write can outlive the next event. Nothing it renders waits on an rpc: a service's release and state path are mirror reads (the release check keeps its `info` reply per lifetime), and lifetime facts only an rpc tells (the vendor catalog, the profile floors) are fetched on a separate task.
- Declare liveliness **after** rpc queryables: serve-side hygiene so a token never precedes the surface at the origin. (Client-side, the matching gate above covers the propagation window this ordering cannot.)
- Zenoh rejects tokio's current-thread scheduler — zenoh-touching tests need `#[tokio::test(flavor = "multi_thread")]`.
- Stale Unix socket files are fine: zenoh's `.lock` protocol takes over an unclean listener path on the next bind.
